# kb page performance in bb, and whether kb should go offline-first

Date: 2026-10-25. Scope: the kb page (`kb ui`, served by shared-server at
`https://kb-popemkt.taild98079.ts.net` and framed by the bb `kb` plugin beside
each thread). Changes: [popemkt/kb#32](https://github.com/popemkt/kb/pull/32) and this repository's PR
`feat/kb-perf`.

The owner's report was that kb is slow on its first load and seems to reload
on every thread switch. Both were true. Every load moved 3.3 MB with no
compression and no caching, over a relayed tailnet link, and bb destroyed and
rebuilt the kb frame on every thread switch.

## How it was measured

- **Live:** a headless Chromium (Playwright 1.62) on the Mac, loading the live
  URL through Tailscale Serve. The Mac reaches shared-server through the DERP
  relay in Singapore (`tailscale ping`: "via DERP(sin)", 120 to 170 ms). Both
  ends have a hard NAT (`MappingVariesByDestIP: true`, no port mapping), so no
  direct path forms. One connection measured about 1.2 MB/s.
- **Before and after:** two `kb ui` processes on the Mac, one on
  `origin/main` and one on the branch, each with a copy of this repository's
  store (118 KB `nodes.jsonl`) and a scratch `KB_HOME`. They were measured
  behind a TCP proxy that emulates that link: 150 ms round trip, a shared
  12 Mbit/s downlink, and one round trip per connect. Through the proxy,
  origin/main transfers a 717 KB chunk in 0.81 s; the live link takes 0.73 to
  0.91 s.
- **Metrics:**
  - *Ready* is the time until the workspace is open: no "loading…" and no
    "Opening your workspace".
  - *Cold* is a fresh browser context.
  - *Warm* is a reload in the same context, which is what a bb panel that
    frames kb again gets.
  - Every figure is the median of 3 runs (live) or 5 runs (emulated).
- The scripts are in the PR description. They are not committed, because they
  are measurement scaffolding.

## Before

### Live, through Tailscale Serve (DERP)

| metric | cold | warm |
| --- | ---: | ---: |
| TTFB (index.html) | 536 ms | 304 ms |
| first contentful paint | 1924 ms | 3308 ms |
| ready (workspace open) | 4172 ms | 5752 ms |
| requests | 35 | 35 |
| transferred | 3328 KB | 3328 KB |
| served from HTTP cache | 0 | 0 |

A warm load was slower than a cold one. No asset carried `Cache-Control`,
`ETag` or `Last-Modified`, and nothing was compressed, so every load fetched
all 3.3 MB again.

### Server work

The server is not the bottleneck:

- `kb ui` starts listening within a second of systemd starting it.
- `/api/graph` answers in 2 to 3 ms on loopback. It is the hub's in-memory
  snapshot, and is 77 KB live and 119 KB for this repository's store.
- `kb.manifest` answers in 2 to 3 ms, but its receipt is 93 to 133 KB. It
  carries the whole action catalogue, while the page follows only its views
  and extensions.
- A load on loopback, where only CPU counts, is ready in about 245 ms both
  before and after.

The time on the live link is round trips and bytes.

### Bundle

- **Eager set.** `index.html` loads its entry and modulepreloads 27 chunks:
  2.23 MB raw, which is 0.62 MB as gzip.
- **Largest contents** (source bytes, by sourcemap):
  - react-dom: 523 KB
  - effect: 2.5 MB of source, tree-shaken
  - zod/v4: 268 KB plus 265 KB (classic and core)
  - DataScript: 456 KB
  - tailwind-merge: 103 KB
  - phosphor icons: 107 KB
- **Lazy routes.** Canvas (214 KB), graph (39 KB plus the force-3d and sigma
  chunks), chart (782 KB) and lab are already lazy and are not in the eager
  set. They did not need to be split again.
- **DataScript on the main thread.** It was there although the page's query
  engine runs in a worker. `@kb/ui-sdk` re-exported `DatascriptIndex` and
  `inThreadPort` for tests. The SDK's whole namespace is the `kb-ext-sdk` host
  module repository extensions import, so every export is live, and
  `datascript-index.ts` kept DataScript in the eager bundle.

### bb rebuilds the frame on every thread switch: confirmed

This was read from bb-app 0.47.0's bundled frontend (`app.asar`) and SDK
0.6.49's types:

- `ThreadSecondaryPanel` renders only the active tab:
  `x.renderContent(...)` for the tab whose id is active. Inactive plugin tabs
  are unmounted, not hidden.
- Each plugin tab mounts with instance id `thread/<threadId>/<tabId>`. The
  React key of its mount element contains that id, so a thread switch destroys
  `KbPanel` and its `<iframe>` and builds new ones. Coming back to a thread
  reloads kb from nothing, which is a warm load (5.8 s live) every time.
- `PluginThreadPanelActionRegistration` is `{ id, title, icon, component,
  layout, run }`. There is no keep-alive, persistent, hidden or mount-strategy
  option, and the props are only `{ threadId, params }`.
- `experimental_appOverlay` is mounted once per app window, outside the
  route-owned layout. It is not keyed by route or thread, and plugin
  components run in bb's own document. That makes it the one host that
  outlives a thread switch.

## What changed

### kb ([popemkt/kb#32](https://github.com/popemkt/kb/pull/32))

1. **One delivery boundary** (`packages/app/server/src/delivery.ts`,
   DESIGN-UI.md → Delivery). The server's `handleHttpRequest` sends every
   answer through `deliver`, which does two things:
   - It answers `304` when a read revalidates the `ETag` it holds.
   - Otherwise it sends a text body (script, style, markup, JSON, SVG, at
     least 1 KiB) in brotli quality 6 or gzip, whichever the client prefers,
     with `Vary: Accept-Encoding`. The encoding is computed once per body per
     process and kept by the body's digest, within a 64 MiB budget.

   `POST /api/action` receipts are compressed too, so the manifest goes from
   93 KB to 12 KB.
2. **Caching by name** (`staticCacheHeaders`, `assets.ts`):
   - Everything under `ui/dist/static/` is the bundler's digest-named output,
     and is sent `public, max-age=31536000, immutable`.
   - `index.html`, the SPA fallback and the public files are sent `no-cache`
     with a weak `ETag` built from size and mtime.
3. **No DataScript on the main thread.**
   - `@kb/ui-sdk` stops exporting `DatascriptIndex` and `inThreadPort`. Tests
     take them from `@kb/ui-test-kit`, and the shell's vitest setup moves into
     `src/test-support/` so it may.
   - `@kb/query` declares `"sideEffects": false`.
   - The eager set falls from 2.23 MB to 1.76 MB raw, and is 493 KB as
     brotli. A gap node records that nothing yet checks this property
     (kb `01M5QK2PFWPD64E846YV9QZWVD`).
4. **The boot asks early.**
   - `index.html` preloads `/api/graph`, so it downloads beside the bundle.
   - The boot asks for `kb.manifest` beside the graph (`readManifest`) and
     follows it once the graph is in.

   This removes two sequential round trips.

### dotfiles (this PR): the bb `kb` plugin keeps each thread's kb tab alive

- **Where the frames live.** `frames.tsx` is an `experimental_appOverlay`
  that holds the window's kb frames. Each recently shown thread keeps its own
  frame, three at most; past that, the least recently shown frame goes, and a
  frame whose panel is shown now never goes (`lib/frames.ts`, tested).
- **The panel tab.** `KbPanel` is now only the place its thread's frame is
  drawn over. It claims that place on mount and releases it on unmount.
- **Positioning.**
  - A frame is never moved in the DOM, because moving an iframe reloads it.
  - It is positioned `fixed` over its place, and clipped (`clip-path`) to
    the place's ancestors that clip overflow, so it never paints over the UI
    beside a scrolled or narrowed panel.
  - One loop in the host draws every frame, each animation frame while any
    place is mounted, and writes only what changed. A place can move without
    resizing, which a ResizeObserver would miss.
  - Otherwise it is `visibility: hidden` and `inert`, and keeps its size so
    it does not lay itself out again when shown.
  - Its z-index is 35, read from bb's bundled classes: above the main column
    (`max-md:z-30`) and the panel resize handles (`z-[25]`), below the mobile
    sidebar scrim and floating thread controls (`z-40`) and every popover,
    menu, dialog, drawer and drag guard (`z-50` and up). bbim's hint layer
    and bb-lively's layer sit above it too.
- **Sessions and config.**
  - Each frame is its own kb tab with its own session, but only a shown
    frame is its thread's tab for the agent. The host reports a thread's
    session when its frame is shown, repeats it every 30 s while it stays
    shown, and reports `null` when the frame is hidden, reloaded or evicted.
    An agent whose thread is not shown acts tabless, as the kb skill says.
    One effect in the host does all of this from the store's `tabs()`.
  - Config is read once per window instead of once per panel mount, and the
    window preconnects to kb's origin as soon as config arrives.
- **The SDK limit** is recorded as a gap (dotfiles
  `01M5QN6PKBQ5YE4FNB1PYPXR92`), with its marker in `frames.tsx`.

Verified in a harness that mounts `KbFrameHost` and remounts a panel keyed by
thread, as bb does. Screenshots are in
`.kb/assets/overnight/2026-10-25/kb-perf/`.

- Through the sequence a → b → a → c → d, each frame's `load` fired exactly
  once.
- Thread a came back on the route it was left on (`/graph/…`).
- Each switch reported the thread left `null` and the thread shown with its
  session; at the limit of three, b was evicted.
- Inside a clipping ancestor 200 px shorter than the panel, the frame was cut
  at the ancestor's edge (`clip-path: inset(0 0 200px)`), followed the
  ancestor's scroll, and took no clicks below it
  (`keepalive-4-clipped.png`).
- A new frame's first session can be the one an older frame said, because
  same-origin frames in one window share `sessionStorage`; kb renews it at
  once, and the next report carries the new one.
- Hidden frames cost nothing: the host ran at 80 fps with two hidden kb frames
  in headless Chromium.
- Showing a kept frame takes one animation frame of the host. In headless
  software GL, the visible kb page's WebGL backdrop slows that frame to 80 to
  270 ms.

## After

Emulated DERP link (150 ms RTT, 12 Mbit/s), median of 5, the same store:

| metric | before cold | after cold | before warm | after warm |
| --- | ---: | ---: | ---: | ---: |
| first contentful paint | 2468 ms | 1604 ms | 2312 ms | 364 ms |
| ready (workspace open) | 3599 ms | 1624 ms | 3427 ms | 483 ms |
| transferred | 3323 KB | 493 KB | 3323 KB | ~0 KB (31 cache hits; `/api/graph` 19 KB br) |
| `/api/graph` starts | 2461 ms | 313 ms | 2307 ms | preloaded |

A bb thread switch behaves as follows:

| case | before | after |
| --- | --- | --- |
| back to a thread shown in the last three | full warm reload: 5.8 s live, 3.4 s emulated | no reload; the kept frame is shown on the next frame, on the route, scroll and selection it was left on |
| to a new thread | full warm reload (same) | a new frame on a warm cache: about 0.5 s on the link; 213 ms in the loopback harness |

The live service picks the kb half up only after the kb PR merges, a nightly
publishes, and this repository bumps the kb pin (`nix run .#github-sources --
update kb`) and the coordinator deploys. The live numbers above are therefore
the "before". The emulated "after" is the projection, because the emulated
"before" matched live within 15%.

## What is left

In rough order of value:

1. **The tailnet path.** Every request pays 120 to 170 ms because the Mac and
   shared-server meet through DERP Singapore; both report hard NAT.
   - A direct path would cut the round trip to the ISP's real latency. The
     options are a UDP port mapping (UPnP or NAT-PMP, or a static forward of
     41641) on either end, or a Tailscale peer relay.
   - This is infrastructure, not kb, but it is the largest single factor left.
     The next cold-load win on the page side is smaller than any round trip
     this removes.
2. **The engine worker.**
   - It is 871 KB raw and 211 KB as brotli: DataScript, effect and zod for
     the worker. It is fetched only once the page hydrates.
   - A `<link rel="prefetch">` or `modulepreload` from `index.html` would
     overlap it with the bundle. That needs a Vite hook to learn the worker's
     hashed name.
3. **The manifest receipt** is 93 KB raw and 12 KB as brotli. The page
   follows `views` and `extensions` only, so a narrower read would save
   parse time and the remaining bytes.
4. **The backdrop.** Unicorn Studio is a 132 KB vendor script plus a WebGL
   scene. It loads after ready but animates continuously. In a bb panel it
   could pause while the frame is hidden, or be off in embedded mode.
5. **The eager bundle** is still 1.76 MB raw: react-dom, effect, two zod
   builds, tailwind-merge and phosphor icons. Collapsing the two zod builds
   into one, and using lighter icon imports, are the next candidates. A
   bundle-budget check (the kb gap above) should land first, so wins stay won.
6. **Flaky test.** `@kb/ui`'s `not-found.acceptance.test.tsx`
   (`/canvas/NOPE`) failed once under machine load in the full `test:ui` run
   and passes alone. The canvas route's lazy chunk races the test's `until`
   timeout. This was already true before this change.

## Offline-first: recommendation

**Do not build an offline-first kb page now.** Caching by name and keeping
frames alive capture almost all of what the owner felt. The two
offline-first pieces each buy little for the bb case, and one of them changes
kb's sync model.

### A service-worker app shell and asset cache

- **What it adds.** After this change, a warm load already takes every asset
  from the HTTP cache. What remains is one revalidation of `index.html` (a
  `304`, one round trip), `/api/graph`, the manifest, and the WebSocket. A
  shell service worker would remove the `index.html` round trip (about
  150 ms) and could open the page with no server at all.
- **The risks:**
  - A shell served stale after a kb upgrade must still find its old chunks.
    `ui/dist` is replaced whole on an upgrade, so an old shell would 404 on
    its chunks unless the worker also caches them, or the HTML is
    network-first, which gives back the round trip.
  - `kb ui` auto-builds and fingerprints `ui/dist`, so a checkout's server
    changes chunk names often.
  - Inside bb's frame, a worker registers under kb's origin. Whether its
    storage is partitioned depends on whether bb and kb are the same site. If
    `ts.net` is a public suffix, the site is `taild98079.ts.net` and both are
    the same site, but that needs checking in the real frame.
- **Verdict.** It is cheap to write but not low-risk, for about one round trip
  per warm load. Revisit it together with the replica below, if offline
  reading becomes a goal.

### A local IndexedDB replica with sync

kb already has most of a replica: a client node set (`BrowserStore`) with a
DataScript engine in a worker, an ordered push lane of invocations, and a
server tx log with revs that the WebSocket catches up from (`since`).
Persisting that replica means two additions:

- **Reads:** the last snapshot and its rev go to IndexedDB, so the page opens
  on local data at once, then asks the server for the txs since that rev.
  This saves the `/api/graph` round trip and the bytes, which are about 19 KB
  as brotli today. It also makes reading work offline.
- **Writes:** the push lane gets a durable outbox. Invocations made offline
  are kept and pushed in order on reconnect. Any whose preconditions moved
  are rebased on the new head, or refused and shown, under the hold rules
  kb already has (DESIGN-UI.md → Replica sync).

**CRDT or kb's tx log.** Stay with the tx log. kb's unit of change is an
action invocation the server re-runs and logs, ids are client-minted ULIDs,
and the JSONL merge already resolves node sets by id (`mergeNodeSets`). A CRDT
such as Yjs or Automerge would buy character-level merging of concurrent
edits to one node's text by two writers. That is rare for a person's own kb,
and it would replace the store's model, not extend it, against Rule 1. Text
inside a node could adopt a CRDT later, scoped to that field, if two people
ever edit one node at once.

### What it buys, given kb is reached over the tailnet from the Mac

Little, for the bb panel:

- bb itself is served from shared-server. When shared-server is unreachable,
  the bb UI that frames kb is gone too, so an offline kb inside bb has nothing
  to sit in.
- The agent's tools reach kb on shared-server, through its socket. A page
  writing to a local replica while offline would show the person a kb the
  agent cannot see until sync.

It buys something for kb opened on its own (a laptop on a plane), and a little
latency: one round trip and about 19 KB, against the 1.6 s cold load. The
latency the owner felt came from bytes and reloads, and both are now gone.

### How it meets "kb local per machine?"

Another agent is researching that question. Two ways it interacts with this
one:

- **If kb runs locally per machine** (a `kb ui` on the Mac over its own
  store, synced by git and the `kb-jsonl` merge driver, or by a sync
  protocol):
  - The page is served from loopback, so a load is CPU-bound, about 250 ms
    here. Offline comes free, and the service-worker question disappears.
  - It would not serve the bb panel as built, for three reasons:
    1. The panel's tab session ties the agent's calls to the same kb server
       the tab talks to. bb's agents run on shared-server, so a Mac-local kb
       splits the person's tab from the agent's store.
    2. A remote bb page framing `http://127.0.0.1` runs into Chromium's
       Private Network Access rules.
    3. Every machine's bb would frame a different kb.
- **An IndexedDB replica is the page-level form of "local".** It keeps one
  authoritative kb server, which the agent and every tab share, and gives each
  machine a local copy for instant open and offline reading. If the other
  research lands on "one server, local copies", this is the copy. If it lands
  on "a server per machine", the replica is unnecessary and the work goes into
  server-to-server sync instead.

**Recommendation:**

1. Keep shared-server's kb as the one server.
2. Fix the tailnet path.
3. Revisit a persisted replica (reads first, then the outbox) only when
   offline reading or writing is an explicit goal. Build the service-worker
   shell in the same change, since they share the invalidation story.
