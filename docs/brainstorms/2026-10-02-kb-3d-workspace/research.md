# 3D brainstorming workspace for kb: evidence pack

Research date 2026-10-02. Scope: gather evidence for a Blender-ish 3D workspace for human+agent brainstorming, with tldraw-quality UX. Prior work not repeated: `docs/brainstorms/2026-09-29-kb-genui-canvas-agents/canvas-2d-3d.md` (call it C23) and `README.md`. Evidence grades: **[P]** primary (official doc/repo/npm registry/release notes fetched today), **[S]** secondary (search snippet, blog), **[U]** unverified / fetched page was thin. Many WebFetch summaries were shallow (docs.blender.org pages came back as navigation text only); where so, I say "known convention" and cite the manual URL as the home, not as proof of detail.

**Things the 3D canvas does NOT have** (all cards are z-planes; no volumes): any real 3D object (box/sphere/pillar/arrow mesh), a transform gizmo, rotate/scale in 3D (only x,y,z translate + orbit camera; cards stay face-on to the canvas plane), 3D grouping, surface snapping, mesh assets (`.kb/assets/` glb planned in C23 section 3, not built), billboarding, per-item rotation fields. `CanvasHitItem` in `canvas-camera.ts:212` is a rectangle on a plane: hit-testing against volumes would need a ray/mesh test (this is the natural place for three-mesh-bvh or plain `Raycaster`).

**Prior decisions that constrain the design** (C23 + README): decision 6 "meaning is nodes, geometry is view settings"; step 7 (canvas items become nodes, `#placement` with x,y,z,rotation,scale,order,parent) is **deferred by the owner 2026-09-30**, step 8 built on the JSON Canvas doc with extra fields that round-trip; C23 recommended "B now": DOM 2D + three 3D joined by one contract (`CANVAS_PROJECTIONS`), keep vanilla three, do not adopt R3F/drei yet, upgrade three r180 to r186 for `HTMLTexture`.

No open-source "tldraw for 3D" turned up: GitHub topic searches returned force-directed 3D mind-map components (`entin-hun/3D-MIND`, `mindorb/mindorb`) and 2D infinite canvases only [S: https://github.com/entin-hun/3D-MIND, https://github.com/mindorb/mindorb]. Nothing combines card-on-plane editing with real 3D objects.

**Takeaways**
1. The successful pattern is **cards-on-planes plus a small set of 3D primitives inside one scene**, not a tilted 2D canvas. ShapesXR (Figma frames + primitives), Spline Hana (2D on the same runtime), Freeform-on-visionOS all do this.
2. Group-then-edit-inside, snapping modes (world/object/all) and pivot-move are recurring "most requested" features (ShapesXR, Spline).
3. Text input is the weak point of every spatial thinking tool (Softspace needs a hardware keyboard). On a screen, keep **text editing in DOM** (an HTML overlay on the picked card), draw static text as texture.
4. Format convergence: **glTF/GLB for objects, USD(Z) as export**, CSV/JSON for graph data. Nobody ships an editable scene format others can read.
5. "Re-centre on this" navigation (TheBrain) and "gather/present" (Arkio) are cheap, high-value camera features for brainstorming.
6. Spline is the closest commercial analogue but closed; none of the products is scriptable by agents except Spline's agent/MCP (C23).

## (c) Blender / DCC conventions: adopt vs skip

Home pages (Blender 5.2 LTS manual): transform https://docs.blender.org/manual/en/latest/scene_layout/object/editing/transform/introduction.html, axis locking `.../transform/control/axis_locking.html`, numeric input `.../control/numeric_input.html`, snapping https://docs.blender.org/manual/en/latest/editors/3dview/controls/snapping.html, pivot https://docs.blender.org/manual/en/latest/editors/3dview/controls/pivot_point/index.html, orientation `.../controls/orientation.html`, navigation `.../editors/3dview/navigate/{navigation,views}.html`, collections https://docs.blender.org/manual/en/latest/scene_layout/collections/index.html, outliner `.../editors/outliner/introduction.html`, gizmo `.../editors/3dview/display/gizmo.html`. **Fetch quality was poor [U]**; the items below are well-known Blender behaviour, confirmed only at the structural level (the transform page confirms G/R/S modal keys, X/Y/Z axis constraint, Shift+X plane constraint, numeric input, Enter/LMB confirm, Esc/RMB cancel; the pivot page confirms bounding-box centre, 3D cursor, individual origins, median point, active element).

| Convention | Verdict | Why |
|---|---|---|
| **Gizmo (arrows/rings/planes) for translate/rotate/scale** | **Adopt** (default for mouse users) | Discoverable; three's `TransformControls` provides it, Spline/ShapesXR/Babylon all ship it |
| **Modal G / R / S + X/Y/Z lock + type a number** | **Adopt, small subset** | Keyboard fast path an agent-era power user expects; costs ~one state machine on top of the existing `use-canvas-keyboard` / tool reducer (`lib/canvas-tool.ts` is already a pure reducer). Skip proportional editing, gimbal |
| **Axis constraint, Shift+axis = plane constraint** | **Adopt** | Essential in 3D because a mouse delta is 2D; kb's current Alt-drag lift is a one-off special case that a constraint model would absorb |
| **Snapping: grid/increment, then object-to-object/surface** | **Adopt grid + "snap onto surface of other object"; skip vertex/edge** | Grid snap is cheap; surface snap makes cards "sit on" shelves (Spline red-plane, ShapesXR object mode). kb's 2D alignment guides (`SNAP_TOL`=5px) become the plane case of the same mechanism. Hold-modifier toggles snapping |
| **Pivot** (bbox centre, individual origins, 3D cursor) | **Adopt bbox + individual; skip 3D cursor at first** | Groups of cards need rotate-about-centre; Spline lets you Cmd-drag the gizmo to move pivot |
| **Local vs global orientation** | **Adopt a toggle (global default)** | Needed as soon as objects rotate; cheap in TransformControls (`setSpace`) |
| **Navigation: orbit/pan/zoom, frame selected (numpad .), frame all, ortho/persp toggle (numpad 5), axis-aligned views (numpad 1/3/7), "view from top" ** | **Adopt**; `fitView`, `orbitView`, `panView`, `zoomViewAt` already exist in `canvas-camera.ts`. Add top/front/side presets and "frame selected". Top-down ortho preset == the 2D projection, which is the bridge for 2D<->3D |
| **Local view (isolate selection)** | **Adopt, cheap** | = "focus this subgraph", maps to kb view filters |
| **Outliner** (hierarchy tree, click to select, eye/lock toggles) | **Adopt, but it is a kb projection** | kb already has an outliner over the same graph (CLAUDE.md "outline is a projection"): selection must sync both ways rather than building a second list |
| **Properties panel** | **Adopt as kb's existing node inspector** | Fields are nodes; transform fields (x,y,z,rx,ry,rz,scale) edit like any field |
| **Collections vs parenting vs groups** | **Adopt a single "group" idea** | Blender separates organisation (collections), dependency (parenting), instancing. For brainstorming one concept (group = parent placement, ShapesXR re-openable) is enough; skip instancing |
| **Quad view** (4 simultaneous viewports) | **Skip for v1** | Overkill; but note step 6 layout view type could host 2D+3D side-by-side later, which is a cheaper "quad view" |
| **Edit mode / vertex modelling, modifiers, shader nodes, rigging, timeline** | **Skip** | Not brainstorming. Predefined primitives only |
| **3D cursor** | **Skip v1** | Replace by "place at camera focus / on picked surface" |
| **Tool-vs-select-box paradigm, right-click-select** | **Skip** | tldraw/Figma convention (click select, V/R/T/N sticky tools) is already in kb |

Platform note (pitfall): Blender's keymap overloads letters; kb's tool letters (V,T,R,O,D,G,N) already collide with Blender's G/R/S. Resolve with "tools only when nothing is selected / modal keys when selection exists" or a modifier, a design decision (see section g).

**Object formats.** (i) **glTF 2.0/GLB** for predefined meshes (every product above imports it; ShapesXR/Gravity Sketch/Womp/Vectary/Spline export it). three's `GLTFLoader`/`GLTFExporter` round-trip `extras` through `userData` (C23). Parametric primitives (box, sphere, cylinder/pillar, cone, torus, plane, arrow = cylinder+cone) should be **parameter records, not meshes**, generated by three geometry classes: they stay tiny in storage, diffable, and agent-writable (`{kind:"box", w,h,d}`), which also matches kb's existing `shape: rect|ellipse|diamond` field. (ii) three.js editor's own JSON uses `ObjectLoader` scene JSON; the editor stores scripts keyed by object uuid (C23). (iii) Index-based glTF references break on insert (C23 formats table); OpenUSD offers path-addressed layers but no practical browser runtime. Recommendation of evidence: store *kb's placement records* (JSON Canvas + extension fields today), generate GLB/USDZ only on export, as C23 already concluded.

## (e) 2D<->3D switching: evidence

1. **kb already implements the strongest known approach**: one document, one camera model where 2D = same camera with `yaw=pitch=fov=0`, bridged to CSS translate/scale by `viewOfPan`/`panOfView` (`canvas-camera.ts:268-285`; `canvas-projections.ts:31`). `lerpView` (:416) interpolates two views, so a dolly transition between them is already possible. The shared contract test proves hit-test/selection/paint-order parity.
2. **Spline Hana** reports the same architecture at the runtime level: 2D and 3D elements "run on the same runtime and effects pipeline", 2D shapes can be converted to 3D "while keeping a live connection" (extrude) [S: https://alternativeto.net/news/2025/12/spline-adds-3d-capabilities-to-its-real-time-design-canvas-hana/; https://docs.spline.design/hana-a-canvas-for-interactivity/3d-shapes-in-hana]. 2D vs 3D *editing* are still separate modes/editors in the product (C23).
3. **tldraw-3d** keeps a single 2D editing surface and renders 3D as an underlay with shared camera [P: https://github.com/OrionReed/tldraw-3d]: shows depth-as-view-of-2D-data (history on Z) without 3D editing.
4. **Figma** adds z-rotation as an *attribute on 2D layers*, exported as CSS 3D transforms [S: explainx recap], i.e. 2.5D on cards.
5. **Blender** itself: top/front/side ortho presets and ortho/persp toggle are the established way to "flatten" a 3D space for precise work [manual, navigation/views pages; U on details].

**Techniques that work**: (a) one scene graph, 2D view = ortho camera looking down -Z with z flattened to draw order (kb does this). (b) Persist the camera per view, not in content (kb GAP `01M3S5DD5W4B3BSZMA6DE8ZVP8`). (c) Dolly-zoom crossfade (C23 4.3). (d) "View filter": which objects are visible in 2D (e.g. real 3D objects drawn as flattened silhouettes or hidden).

**Pitfalls (from kb's own history and the sources)**
- **Text legibility**: textured cards blur when scaled/tilted; kb pays DPR x1.5 textures and has an open GAP; vector/MSDF text is the usual remedy. Face-on 2D should use DOM (sharp) while 3D uses textures.
- **Selection semantics**: in 3D a click can hit a card behind another; kb resolves with `paintPlanes` depth tie-break. Volumes need ray-mesh hits and a rule for "enter group vs select group" (ShapesXR: groups re-openable).
- **Gizmo vs 2D drag**: moving a card in 2D must map to an in-plane translate; rotated objects make "move in plane" ambiguous. Blender's global/local orientation and axis constraints solve this explicitly.
- **Arrows/connectors in 3D**: kb edges are SVG beziers in 2D and a 3D edge layer exists (`canvas-scene-edges.ts`); once endpoints are rotated 3D objects, an arrow needs anchor points on the object (face/edge midpoints) and routing in 3D; CSS3D/overlay arrows will not occlude correctly.
- **Scale**: CSS/DOM cap and texture memory budget (C23 suggests switching to GPU cards if DOM projection passes ~2k visible items [C23 4.3]).
- **Undo/camera**: camera moves must stay outside content undo (kb already excludes camera from history).
- **Rotation fields**: JSON Canvas has none; adding `rotation`/`scale`/`kind` to items goes in `extra` today (round-trips) but is the same "second storage shape" smell C23 warns about, which is why decision 6/step 7 matter.

## (f) Agent notes (brief)

- **Blender MCP is the dominant prior art**: socket server in the app + MCP server; tools = `get_scene_info`, create/modify/delete objects, **`execute_blender_code`** (arbitrary Python), materials, asset search, render; 29.9k stars, MIT; README warns to save before using exec; large operations must be split into small steps [P: https://github.com/ahujasid/blender-mcp]. Another implementation offers a safe mode that vets scripts [S: https://pypi.org/project/blender-llm-mcp/]. Matches tldraw offline's exec model in C23.
- **SceneActBench (2026)**: agents act on Blender scenes through four tools (scene inspect, object inspect, code exec, render). Scores 38.6-50.2 overall; layout/furniture placement is best (84.1) while camera pose estimation (34.5) and 3D reconstruction (12.3) are poor; more interaction steps did not correlate with better results; photorealistic or multi-view renders helped some models and hurt others by up to 17.3 points [P: https://arxiv.org/html/2607.22393v1]. Read: **LLMs place objects decently relative to other named objects but are weak at raw coordinates, camera, and rotation.**
- Scene-graph prompting is the standard mitigation: LLMs have "limited spatial perception capability", so give a relation graph rather than raw coordinates [S: https://aclanthology.org/2025.acl-long.1036.pdf (LLM Meets Scene Graph)].
- Design implications (inference, flagged): expose **relational placement verbs** (`place_near(id, target, side, gap)`, `stack_on`, `align`, `arrange(ids, layout:"ring|grid|layers")`, `connect`, `group`), return a `describe()` of nearby objects with relations and bounding boxes rather than raw matrices, snap to grid/surface server-side, and offer `screenshot(view)` for verification. kb already has `canvas.describe` and lints-as-diff planned (C23 4.4); add 3D lints (overlap/intersection, off-camera, floating-in-air if "shelf" semantics are chosen).
- kb is a graph: relationships (`:node/mentions`, ref props) can generate 3D layouts the agent never has to coordinate (the existing force3d graph and `layers` already do this).

## (g) Open questions for the designer

1. **Is 3D one canvas with a projection toggle, or does "3D space" become a different view type?** Evidence favours one scene model and two cameras (section e), which kb already has; the remaining question is whether real 3D objects live in the same JSON Canvas doc (via `extra`, per owner's step-7 deferral) or require step 7 first (placements as nodes, C23 4.1). Rule 1 says a rotation/kind extension bag is the "bolt-on" shape.
2. **What is an "object"?** Proposal from evidence: a small closed set of parametric kinds (card, sticky, frame, box, sphere, cylinder/pillar, cone, plane/shelf, arrow/connector, group) as one tag/enum with a `kind` field, glTF only for imported assets. Does a primitive carry a kb node (meaning) like a card, or is it pure decoration? "Everything is a node" says node.
3. **Gizmo or modal keys first?** Both are cheap on TransformControls; which keymap wins when tool letters (G, R) collide with Blender's G/R/S?
4. **TransformControls (addon) vs `@pmndrs/handle` vs custom** for the gizmo: TransformControls works with WebGPURenderer per forum evidence but has no official webgpu example; the custom route reuses `hitTest`/`screenToPlane` and avoids a second camera/pointer model.
5. **Rotation model for cards**: do cards ever rotate away from face-on? That changes `CanvasHitItem` (rectangle on a plane) to an oriented quad and the 2D projection ("flatten rotated items?").
6. **Where does text editing happen in 3D?** DOM overlay on the picked card vs HTMLTexture (Chrome-only, API still moving until at least Chrome 160). Texture budget GAP (`01M3S5DDC3JYX8871YMJ7C6PAN`) should close first or alongside.
7. **Connectors**: anchors on objects, 3D routing, occlusion/depth-fade; how a drawn 3D arrow becomes a kb ref (kbLink `native` vs `layout` modes exist for 2D).
8. **Selection/outliner sync**: reuse the outline as the Blender outliner; define "enter group" semantics.
9. **Camera ownership**: finish the camera-to-view-node migration (GAP `01M3S5DD5W4B3BSZMA6DE8ZVP8`) before adding top/front/side presets and saved camera bookmarks.
10. **Three upgrade (r180 -> r186)**: needed for `HTMLTexture`; r186 released 2026-09-24. Do object/gizmo work on r180 or after the upgrade?
11. **Agent surface**: relational verbs plus exec? Is there a lint set for 3D (intersection, floating, occluded labels)?
12. **R3F decision gate**: drei v11 and R3F v10 are alpha (2026-09-05 / 2026-09-08); stable v9 works with an async WebGPURenderer but drei's WebGPU story is unfinished. Is there any reason to move before v10 stabilizes?
