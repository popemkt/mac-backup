Set up kb's MCP edge

One-time setup on shared-server, so Gemini and Claude can reach your kb after a Google sign-in. Follows docs/mcp-edge.md → One-time steps, which wins wherever the two differ.

Good to know: three settings, as you decided
  • Restarts keep you signed in. A reboot, an upgrade or a Keycloak restart leaves Gemini and Claude signed in. Signing everyone out is a command of its own: sudo mcp-edge-secrets revoke-all (step 7). The sign-in settings still come from the dotfiles repo: every start puts them back as declared, and removes anything added by hand.
  • A sign-in lasts 30 days at most, and ends sooner after 14 days without use. Then the connector asks you to sign in again: one Google sign-in, nothing on the server (step 7).
  • Only hoangng71299@gmail.com gets in. To change the list, edit my.stacks.kb.stores.kb.remoteMcp.emails in hosts/shared-server/default.nix.

    Step 1 of 7 · in your browser

    Create the Google sign-in client

    People sign in to the edge with Google. Google needs a client for it, and the one address it may send you back to.

    Do this

    1. Open Google Cloud console → APIs & Services → Credentials. Use any project; a new one called “kb edge” is fine.
    2. Choose Create credentials → OAuth client ID, with application type Web application. The name is up to you.
    3. Under Authorized redirect URIs, add exactly this one address: 
      https://shared-server.taild98079.ts.net/realms/kb/broker/google/endpoint
    4. On the OAuth consent screen (newer consoles: Google Auth Platform → Audience), add yourself as a test user, or publish the app. It asks only for these scopes: 
      openid email profile
    5. Keep the window with the Client ID and Client secret open for step 2. Don't paste them anywhere else: this page has no field for them, on purpose.

    Check it worked

    In the console, open the client you just made. You should see:

    Type                      Web application
Authorized redirect URIs  https://shared-server.taild98079.ts.net/realms/kb/broker/google/endpoint
                          (exactly one, no others)

    And on the consent screen, your address under Test users, unless you published the app.

    Step 2 of 7 · on shared-server

    Put the Google client on shared-server

    The server reads the client ID and secret from two files that only root can open. They never go into git, a chat or this page. One command asks for both.

    Do this

    1. From any machine, run: 
      ssh -t shared-server sudo mcp-edge-secrets google
    2. Paste the Client ID and press Enter. Then paste the Client secret and press Enter: it is not shown as you type, on purpose.
    3. It warns if a value does not look like Google's, and saves it anyway. Fix a typo by running it again.
    Without the command 
    sudo install -d -m 0700 /var/lib/mcp-edge/secrets

    Then run each of these, paste the value, press Enter, then Ctrl-D:

    sudo sh -c 'umask 077; cat > /var/lib/mcp-edge/secrets/google-client-id'
    sudo sh -c 'umask 077; cat > /var/lib/mcp-edge/secrets/google-client-secret'

    Check it worked

    It never prints a secret, and neither does this:

    sudo mcp-edge-secrets status

    You should see both Google files, readable by root only (the rest come in step 3):

    /var/lib/mcp-edge/secrets  700 root (directory)
  google-client-id         400 root, 1 min old
  google-client-secret     400 root, 1 min old
  client-claude-secret     missing
  client-gemini-secret     missing
  keycloak-admin-secret    missing

    Switch it on

    One switch in the host file turns on the sign-in service, the token check, kb's remote MCP server and the tailnet address.

    kb is ready. kb's pinned release has kb mcp --listen (kb PR #294). To confirm, in a checkout:

    scripts/dev kb mcp --help | grep -- --listen

    One line mentioning --listen means it's there. The pin has it since 0.3.1-nightly.20261124162930; no output would mean an older checkout: pull first.

    Do this

      emails = [ "hoangng71299@gmail.com" ];

      mcpEdge = true;
    3. Commit and push to main. On shared-server, rebuild applies only a clean checkout at origin/main.
    4. On shared-server, pull, then rebuild in the background, so it finishes even if your session ends:

      nohup rebuild > ~/rebuild.log 2>&1 &
      tail -f ~/rebuild.log

    You should see:

    The first start added a secret for each client, and one for the edge's own admin:

    client-claude-secret  client-gemini-secret  google-client-id  google-client-secret  keycloak-admin-secret
    curl -s -o /dev/null -w '%{http_code}\n' -X POST https://shared-server.taild98079.ts.net/mcp

    Step 4 of 7 · in the dotfiles repo, then on shared-server

    Open it to Gemini's and Claude's servers

    Gemini and Claude connect from their own servers, not from your devices. A tailnet-only address is invisible to them, so not even the first sign-in can start. Funnel puts the same address on the internet, with its own switch.

    Why this is safe before step 5

    1. Only the edge's 18 allow-listed paths are published at all, and the edge answers “not found” to anything else.
    2. /mcp needs a token from a Google sign-in by an allowed account.
    3. Gemini's list of return addresses is still empty, so every Gemini sign-in is refused until you add its address in step 5.

    Do this

    1. In hosts/shared-server/default.nix, flip the second switch: 
      mcpFunnel = true;
    2. Check that the tailnet policy allows Funnel for this machine: 
      scripts/dev scripts/check-tailscale-policy.sh check

      You should see it count one Funnel:

      ok: the policy grants and auto-approves all … declared Tailscale Services, and allows all 1 declared Funnels
    3. Commit, push to main, pull and rebuild, as in step 3. The policy in configs/tailscale/policy.hujson reaches your tailnet once it's on main.

    Check it worked

    tailscale funnel status

    On shared-server, every line under the address is one of the allow-listed paths, and nothing is mounted at /:

    https://shared-server.taild98079.ts.net (Funnel on)
|-- /mcp         proxy http://127.0.0.1:4190/mcp
|-- /resources/  proxy http://127.0.0.1:4190/resources/
…                18 paths in all; no line for / alone

    No “(Funnel on)”? Funnel comes on only while port 443 serves exactly those 18 paths. journalctl -u tailscale-services -b says why not, for example an adhoc share on 443 (free it with sudo tailscale serve --https=443 off).

    Then, from a device not on your tailnet, such as your phone with Tailscale off:

    curl -s https://shared-server.taild98079.ts.net/.well-known/oauth-protected-resource/mcp

    You should see one line of JSON (wrapped here):

    {"authorization_servers":["https://shared-server.taild98079.ts.net/realms/kb"],
 "bearer_methods_supported":["header"],
 "resource":"https://shared-server.taild98079.ts.net/mcp",
 "scopes_supported":["openid","email","profile"]}
    curl -s -o /dev/null -w '%{http_code}\n' https://shared-server.taild98079.ts.net/admin/

    Anything off the list is not found:

    404

    Step 5 of 7 · Gemini, then shared-server

    Connect Gemini

    Google publishes Gemini's return address only as a pattern, and the edge accepts exact addresses only. So the first try is refused on purpose: it shows you the exact address to add.

    Values

    Server URL
    https://shared-server.taild98079.ts.net/mcp
    Client ID
    gemini

    Do this

    1. On gemini.google.com, turn on Developer Mode, then choose Connect to an MCP server and paste the server URL.
    2. Open Show more (additional settings) and enter the client ID. For the client secret, print it on shared-server and copy it straight into the Client secret field: 
      ssh -t shared-server sudo mcp-edge-secrets client gemini
      Without the command
      sudo cat /var/lib/mcp-edge/secrets/client-gemini-secret
    3. Connect.
    4. The first time, it stops at “Invalid parameter: redirect_uri”. That's expected.
    5. On shared-server, read the address the edge refused: 
      journalctl -u keycloak | grep -o 'redirect_uri="[^"]*"' | tail -n 1

      Something like:

      redirect_uri="https://oauth-redirect.googleusercontent.com/r/…"
    6. Add it, exactly, in hosts/shared-server/default.nix. A * anywhere is refused when the configuration is built. 
      gemini.redirectUris = [ "https://oauth-redirect.googleusercontent.com/r/…" ];
    7. Commit, push, pull and rebuild, as in step 3. Wait for the rebuild to finish: it re-applies the sign-in settings (nobody is signed out).
    8. Connect again in Gemini. Sign in with Google, and accept “gemini wants access to your account”.

    Check it worked

    Ask Gemini: “search my kb for …”, with a word you know is in it. It should answer with matching notes. On shared-server:

    journalctl -u mcp-edge-oauth2-proxy -n 5 -o cat

    You should see lines with your address and status 200:

    127.0.0.1 - … - hoangng71299@gmail.com […] shared-server.taild98079.ts.net POST … "/mcp" HTTP/1.1 "…" 200 …

    If a later connection is refused with a different address, Gemini changes it each time. That would need a pattern instead of an exact address, which is your decision (docs/mcp-edge.md → Gemini's redirect).

    Step 7 of 7 · for later

    Keep these handy

    You're set up. These are the four things you may need later. All run on shared-server; sudo mcp-edge-secrets -h lists the rest.

    Turn it off

    For good: set mcpEdge = false; in hosts/shared-server/default.nix, then commit, push, pull and rebuild. Your own kb app is untouched. Right now, until the next rebuild, stop the edge and take its public address down:

    sudo systemctl stop mcp-edge-oauth2-proxy kb-remote keycloak
    sudo tailscale serve --https=443 off

    The second removes everything mounted on port 443 and its Funnel (adhoc off leaves a declared port alone). The next rebuild puts both back.

    When the sign-in expires

    After 30 days, after 14 days unused, or after Sign everyone out below, Gemini or Claude asks you to reconnect (or sign in) on the kb connector. Click it, sign in with Google, and approve if asked. Nothing to do on the server, and no new secret. Only after Replace a client secret do you also paste the new secret into the connector first.

    For Gemini (or claude). It makes a new secret and puts it in place; nobody else is signed out. Then print it and paste it into the connector.

    sudo mcp-edge-secrets rotate gemini

    Sign everyone out

    Every session and token ends at once, and both connectors ask you to sign in again. It asks before it does anything. A reboot or a restart does not do this.
