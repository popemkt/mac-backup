## 1. Executive verdict

`tools/kb` is unusually deliberate. Its core model, package topology, runtime
composition, storage seam, extension mechanism, typecheck policy, lint policy,
and generated views show substantially more first-principles design than a
typical TypeScript workspace.

It is not yet fully self-steering.

The repository is strongest at expressing intended structure and preventing
new structural drift. It is weaker at proving that its governance records are
true, that exceptions are still live, that all advertised expansion seams are
admitted, and that a green local or remote signal actually blocks invalid
progression.

The most accurate short description is:

> Architected core; evolved UI; partially closed governance loop.

Current confidence by area:

| Area | Confidence | Summary |
| --- | --- | --- |
| Core model and contracts | High | Coherent node model, schemas, receipts, and protocols |
| Runtime composition | High, with one correctness hole | Good Layer/registry seams; action outputs are not validated |
| Persistence | Medium-high | Clear Effect-native direction, but two store interfaces remain live |
| Package organization | High | Automatic discovery, tags, catalogs, curated entrypoints |
| Package constraint enforcement | Medium-high | Broad harness coverage, but deep and relative imports can bypass it |
| Extension expansion | Medium-low | Thoughtful contribution model; repository extensions fail open outside admission |
| UI architecture | Medium-low | Explicit ownership prose, but large modules and cross-surface imports violate it |
| Exception governance | Medium | Gaps and ratchets are visible; lifecycle and rule linkage are incomplete |
| Documentation truth | Medium | Generated bytes are fresh; semantic and canonical prose drift remains |
| End-to-end admission | Medium-low | Hooks and CI exist, but local skips and absent branch protection leave escape paths |
| Agent-led expansion | Medium | Good local instructions; agents still need human architectural review |

Overall confidence is approximately **7/10**. A careful maintainer can expand
the system confidently. An autonomous agent cannot yet rely on the harness to
catch every structurally or semantically harmful addition.

## 3. What changed during the review

The repository advanced while reconnaissance was running. The harness was
moved from `tools/kb/packages/harness` to root tooling at `tools/kb/harness`.
The following earlier findings were genuinely improved or closed by that work:

- the harness is no longer a product workspace package with a synthetic
  `layer:tooling` / `scope:tooling` classification;
- it has a reverse fence forbidding imports from the product into the checker;
- its direct relative imports into `@kb/model` were removed;
- import and re-export discovery now uses `oxc-parser` instead of line regexes;
- side-effect imports, re-exports, literal dynamic imports, comments, and parse
  failures receive substantially better treatment;
- lint and typecheck measurement includes the root harness rather than silently
  measuring only `packages/`.

These changes improve the design because the harness is now structurally
outside the thing it checks. They do not close consumer-side deep imports or
relative imports between product packages.

## 5. Architectural strengths

### 5.1 The node model is coherent

"Everything is a node" is not merely a slogan. Fields, tags, allowed values,
queries, rules, and gaps participate in the same model. This keeps new
capability inside one conceptual system and reduces bespoke storage or editing
surfaces.

The model earns depth: callers learn a small set of node, property, reference,
and tag concepts while the implementation provides search, datalog, backlinks,
rendering, templating, subscriptions, and multiple interaction surfaces.

### 5.2 The package topology is readable

The two package axes are strong:

- `layer:*` captures semantic dependency direction;
- `scope:*` captures runtime portability and the isomorphism fence.

The matrices live in `tools/kb/harness/src/constraints.ts`. Workspace packages
are automatically discovered and checked for:

- exact `@kb/<directory>` identity;
- private ESM manifests;
- one known layer tag and one known scope tag;
- typecheck configuration;
- workspace dependency notation;
- catalog-owned external versions;
- one curated package entrypoint or an explicitly empty surface.

This is an excellent base for agent navigation because a new package cannot
quietly remain invisible to Nx, lint, or typecheck merely by omitting a list
entry.

### 5.3 Runtime composition has good seams

Effect Layers, `Context.Service` usage, typed domain errors, action receipts,
schema-based inputs, storage adapters, contribution decoding, and failure
isolation provide strong locality. The runtime registry centralizes action
discovery and invocation rather than asking each CLI/MCP/UI surface to repeat
the behavior.

The extension model is also conceptually strong: core owns mechanism;
repository extensions own policy. Namespaced contributions, validation, and
template/action unification are the right abstractions.

### 5.4 Determinism is treated seriously

The codebase includes deterministic time/random seams, deterministic
simulations, property testing, write locking, schema parsing, typed receipts,
and a deliberate separation between hard gates and noisy sensors.

The design correctly refuses to treat mutation score as a deterministic merge
truth. That distinction should be generalized to every constraint.

### 5.5 Canonical-source instincts are strong

Examples include:

- one root dependency catalog;
- workspace dependency notation;
- one lint configuration;
- parsed compiler constraints;
- generated rule/todo views;
- `CLAUDE.md` as a symlink to canonical `AGENTS.md`;
- explicit gap nodes instead of invisible workarounds.

The repository already contains most of the primitives needed for a closed
governance loop. The remaining work is principally to connect them.

## 6. Findings by priority

### P0 — correctness: action output schemas are a dead seam

`ActionDefinition` requires an `outputSchema` in
`tools/kb/packages/contract/contracts/src/actions.ts`, and manifests publish it. Runtime
invocation in `tools/kb/packages/app/runtime/src/registry.ts` validates input, runs
the handler, and wraps the raw output in a successful receipt without parsing
it through the declared output schema.

Consequences:

- an extension can return a malformed output that crosses every surface as
  success;
- the public manifest promises a contract the runtime does not enforce;
- output schemas look like coverage while being a dead seam;
- callers must either trust output or add duplicate validation.

Required shape:

1. one canonical output parser in the registry;
2. both Effect-native and Promise handlers pass through it;
3. mismatch maps to an internal contract failure, not invalid user input;
4. red tests cover built-in and extension handlers returning invalid output.

### P0 — admission: repository extensions fail open outside verification

`tools/kb/packages/application/operations/src/extension-loader.ts` discovers
`.kb/extensions/*.ts`, collects load/decode failures, warns, and skips invalid
contributions. Failure isolation is correct for runtime availability, but it is
not sufficient for repository admission.

Current problems:

- `.kb/extensions` is outside package lint/typecheck scope;
- a malformed repository-owned extension can land and silently disappear;
- pre-commit KB verification is primarily triggered by changes under
  `tools/kb/`;
- generated docs being byte-clean does not prove every extension loaded;
- loader tolerance and admission strictness are conflated.

Add a fail-closed `ext validate` operation over the repository's actual
extensions. It should compile, decode contributions, reject duplicate IDs,
validate handlers against their definitions, and require zero loader failures.
Runtime discovery may remain tolerant after admission is strict.

### P0 — enforcement: package dependency fences have bypasses

`tools/kb/harness/src/import-graph.ts` now parses complete TypeScript module
syntax, but `importEdges()` creates workspace edges only for exact
`@kb/<package>` specifiers. It misses:

- `@kb/model/internal`;
- `../../model/src/internal.ts`;
- other relative paths that cross a package root;
- source extensions outside `.ts` and `.tsx`.

`public-surface.test.ts` validates the barrel's shape. It does not validate how
consumers enter the package.

Required shape:

- resolve relative specifiers to an owning package;
- reject any relative import crossing package roots;
- reject `@kb/<package>/<subpath>` imports;
- explicitly govern `.js`, `.jsx`, `.mts`, and `.cts`, either by prohibition
  or inclusion;
- retain the AST parser and add red cases for each bypass.

### P0 — progression: local and remote admission are not fail-closed

The pre-commit hook warns and skips KB checks if required dependencies are
missing. It checks the working tree rather than a reconstructed staged
snapshot, so an unstaged fix can mask a staged defect.

CI installs dependencies and runs verification, but branch protection remains
a documented manual step. Failed checks therefore do not necessarily prevent
`main` from advancing.

For "wholly steered" progression:

- make verifier dependencies a hard, recoverable session prerequisite;
- run KB admission against the staged snapshot;
- trigger it for `.kb/`, `.kb/extensions/`, `AGENTS.md`, governance docs,
  `tools/kb/`, and the hook/workflow itself;
- require the Nix and KB checks through branch protection;
- distinguish local convenience sensors from actual enforcement metadata.

### P1 — governance: the rule index is not an honest enforcement inventory

There are 26 `#rule` nodes:

| Recorded enforcement | Count |
| --- | ---: |
| `prose` | 22 |
| `hook` | 2 |
| `harness` | 1 |
| `lint` | 1 |
| `tsc` | 0 |
| `ci` | 0 |

Thirteen of the 22 prose rules nevertheless name an existing harness, lint, or
TypeScript gate. Nine rules omit `gate` entirely. This contradicts the
canonical promise that `prose` means nothing checks the rule.

The clearest contradiction is the Module boundaries rule: it names Oxlint
`no-restricted-imports`, but that rule does not exist in the live lint config.
The actual partial enforcement is the harness boundary suite.

Six rule homes point into dated wave artifacts, and multiple gates contain
historical labels such as `(w1)` or `(g2)`. The index therefore exposes edit
history rather than a timeless current contract.

Fix the model, not just the rows:

- make every rule atomic enough to have one enforcement classification;
- add a `#check` node or equivalent machine-readable checker registry;
- make `gate` a reference, not free text;
- derive enforcement from the check's actual execution surface;
- validate that the check exists and is invoked by `verify`/hook/CI as claimed;
- validate rule home paths and anchors;
- move historical evidence out of the canonical home.

### P1 — governance: gaps are structured but not lifecycle-safe

There are 42 tagged gap nodes:

- all 42 contain one `expected`, `current`, `impact`, and `closes` value;
- three carry `status=done` but remain rendered alongside active gaps;
- only 3/42 reference a governing rule;
- TypeScript source contains 48 marker occurrences representing 29 unique
  valid gap IDs;
- none of those 29 code-attached gaps links to a governing rule;
- 23 unique gaps suppress `complexity`, but none links to the Code-unit
  cohesion rule.

The harness proves only:

```text
marker -> existing node tagged #gap
```

It does not prove:

```text
active code gap -> live marker
gap -> governing rule
closed gap -> no live marker
current description -> still true
required fields -> singleton, non-empty, correctly typed
```

The marker scan is limited to `.ts`/`.tsx` and excludes the harness. It cannot
govern natural exception sites in shell, JSON, Markdown, Nix, manifests, or
the checker itself. Its JSONL reader also tolerates malformed lines rather
than failing the governance audit.

At least one gap describes implementation already closed by the extension
template registry, and another begins with "Closed" while remaining an active
gap.

Every gap should have required status:

- `open` — expected to close;
- `accepted` — intentionally retained, reviewed on a cadence;
- `blocked` — closure depends on a named condition;
- `closed` — no active exception sites.

The generated view should separate active, accepted, blocked, and historical
gaps. Code markers may reference only non-closed gaps.

### P1 — deterministic debt: Knip is neither gate nor ratchet

`tools/kb/package.json` runs Knip with `--no-exit-code`. Current output contains
73 issue entries:

| Category | Count |
| --- | ---: |
| Unused development dependencies | 9 |
| Unused exports | 40 |
| Unused exported types | 18 |
| Namespace export findings | 5 |
| Duplicate export group | 1 |

The command exits zero, has no baseline, permits growth, and does not detect
stale ignores. CI nevertheless describes the step as dead-code verification.

These are deterministic facts. Either configure Knip accurately enough to
reach zero and make it hard, or feed stable finding identities into the same
ratchet abstraction used for lint debt. Do not create a second exception
system.

### P1 — exceptions: suppression hygiene is inconsistent

Across product packages and the root harness:

- 70 lint-disable directives;
- one `@ts-expect-error`;
- 45 of the 71 total exceptions carry `GAP [[id]]`;
- 26 do not carry structured debt linkage;
- nine are bare, with no GAP and no useful inline reason;
- several use `eslint-disable-next-line` despite the documented
  `oxlint-disable-next-line` convention;
- a strict unused-directive run found four stale suppressions.

Observed rule distribution includes:

| Rule | Approximate sites |
| --- | ---: |
| `complexity` | 23 |
| `react-hooks/exhaustive-deps` | 12 |
| `promise/always-return` | 7 |
| `react/no-array-index-key` | 6 |
| `unicorn/prefer-add-event-listener` | 4 |
| `typescript/no-unsafe-type-assertion` | 4 |
| `eslint/no-await-in-loop` | 4 |
| Other seam-specific rules | 10 |

Four suppressions were already unused when checked with
`--report-unused-disable-directives`, including sites in
`ontology-page.tsx`, `canvas-page.tsx`, and `view-config.ts`.

Add a deterministic suppression parser requiring exactly one form:

```text
// oxlint-disable-next-line <rule> -- GAP [[id]]
// oxlint-disable-next-line <rule> -- <permanent seam reason / decision>
```

A temporary exception should reference an open `#gap`. A permanent exception
should reference a `#decision` or carry a tightly defined sanctioned reason.
Unused directives must fail.

### P1 — ratchets permit backsliding after partial improvement

The committed lint baseline is:

- 40 `max-lines-per-function` warnings;
- 2 `max-lines` warnings.

Increases fail and reaching zero forces promotion. However, a decrease above
zero is only printed. If the count falls from 40 to 10 without lowering the
baseline, it may later grow back to 40 while remaining green.

A monotonic ratchet must fail on any mismatch. A decrease should require an
intentional baseline update in the same change.

Collectors also catch Oxlint/tsgo execution and JSON-decoding failures and
turn them into partial or empty counts. Every collector should return health
plus findings, and the harness should fail unless the tool executed and its
output decoded completely.

### P1 — UI ownership is prose-only and already violated

`tools/kb/packages/app/ui/ARCHITECTURE.md` defines surface ownership and says
cross-surface reuse goes through primitives or `lib/`. Live examples contradict
that model:

- graph imports ontology and sidebar internals;
- ontology imports outline markdown rendering;
- canvas imports outline `NodeContent`, `NodeRow`, and `Bullet`;
- preferences and outline-specific field UI have also crossed ownership lines.

The largest structural hotspots are:

| Module | Approximate lines | Concern |
| --- | ---: | --- |
| `components/canvas/canvas-page.tsx` | 1,835 | Canvas lifecycle, interaction, layout, and rendering mixed |
| `actions/plan.ts` | 1,334 | Broad planning and execution responsibility |
| `actions/mutations.ts` | 831 | Large mutation surface and orchestration |
| `stores/outline.store.ts` | 822 | Multiple state domains in one store |

`CanvasPage` was also the graph's largest complexity hotspot, with cyclomatic
complexity around 134 and cognitive complexity around 218.

These modules are not problematic merely because they are long. Their
interfaces do not hide a coherent body of behavior; multiple responsibilities
and reuse paths leak across surface folders. That makes them shallow at the
architectural level even when internal helper functions exist.

Before adding major UI capability:

1. introduce a path-level UI dependency matrix in the harness;
2. identify actual shared behavior and promote it to named primitives;
3. split pages by owned behavior and lifecycle;
4. keep surface folders dependent on primitives, never on sibling page
   implementations;
5. require every new surface to declare its allowed dependencies.

### P2 — typecheck coverage proves metadata more than execution

Workspace admission currently requires `scripts.typecheck` to be a string. A
package can therefore provide `"typecheck": "true"` and satisfy the structural
check while doing no checking.

The scope model reads tsconfig `include` but does not fully model `exclude`.
JavaScript-family source extensions are also outside several scanners.

Prefer one canonical typecheck target derived by the workspace, or require the
exact approved command and tsconfig path. Forbid unmodeled `exclude` entries or
make the coverage calculation honor them.

### P2 — public SDK compatibility is a manually maintained mirror

`@kb/ext-sdk` contains a dependency-free public contract mirror, a decoder,
and filesystem emission responsibilities. Freshness tests prove that generated
text matches the maintained mirror, while runtime-contract checks cover only a
small set of substrings.

The important missing property is bidirectional compatibility between the
public SDK contract and the runtime contract. Add compile-time assignability
or exactness fixtures in both directions, or generate both from one
dependency-free canonical contract.

### P2 — core action registration is a multi-file ritual

Operations exports action definitions and Effect handlers separately. Runtime
then imports and manually pairs every item in `CORE_ACTIONS`.

Export one canonical `coreActions` contribution collection from operations.
The registry should consume the same contribution interface used by
extensions. This makes addition natural and reduces the chance of a declared
definition or handler becoming unwired.

### P2 — two persistence interfaces remain live

`tools/kb/packages/contract/contracts/src/store.ts` exposes both Promise `Store` and
Effect-native `EffectStore`; `KbContext` carries both styles.

The Effect-native interface is the intended deep seam. Retire the Promise
facade after migrating legacy extension handlers, or record the dual interface
as an explicit transitional gap with closure criteria.

### P2 — some package interfaces are broader than their concepts

Examples:

- `@kb/operations` combines action implementations, CLI mapping, rendering,
  saved queries, persistence helpers, assets, and documentation materialization;
- `@kb/store-jsonl` publicly exports locking and durable-replace helpers used
  only by its own implementation;
- `@kb/ext-sdk` owns contract mirroring, runtime decoding, and filesystem
  generation;
- extension entrypoints called curated barrels sometimes contain the complete
  implementation rather than only selecting exports.

Use the deletion test: if removing a package moves several unrelated bodies of
knowledge into different callers, it owns too much. Deepen around the concepts
that actually vary; do not create packages merely to reduce file size.

### P2 — current documentation does not always read as timeless

Examples observed during review:

- `DESIGN.md` contains server/view statements that no longer match the
  implementation;
- older milestones and execution history remain embedded in normative design;
- `packages/app/ui/ARCHITECTURE.md` names the stale path `tools/kb/ui`;
- the UI architecture records Storybook as rejected while Storybook 10 is now
  installed;
- `DESIGN.md` and `.gitignore` disagree about `nodes.jsonl.lock`;
- `docs/ci.md` still describes older npm/Vite+ commands and a separate UI
  typecheck while CI invokes `bun run verify` and Nx includes UI;
- project-graph commentary and import-graph measurements have historically
  disagreed about whether Nx observes source imports;
- more than 150 wave documents preserve useful history but compete with the
  current design narrative.

Separate:

- current normative design;
- architecture decisions with context and status;
- historical plans, waves, and execution reports.

Rules should link to current homes and stable anchors. Historical reports may
explain why, but they should not be the only home of a live rule.

### P2 — wall-clock assertions are fragile deterministic gates

The store and palette performance tests use hard wall-clock thresholds. Under
concurrent agent load they failed dramatically; run in isolation, both passed.

Keep algorithmic properties deterministic. Treat absolute timing as an
advisory trend or normalize it against a host calibration. A noisy clock should
not determine repository admission unless the execution environment is
controlled.

### P2 — test isolation is incomplete

Running the full suites rewrote the tracked fixture
`tools/kb/.kb/nodes.jsonl`. Tests should use explicit temporary roots created
per test and verified to lie outside the repository fixture paths. Add a
post-suite dirty-tree or fixture-hash red case for integration tests that touch
storage.

## 8. One governance model for deterministic and semantic constraints

Do not create another checklist, policy database, or LLM-specific rules file.
Use KB nodes for the entire chain:

```text
#rule -> #check -> finding or measurement -> #gap / #decision -> review receipt
```

### 8.1 Proposed rule fields

Each atomic `#rule` should carry:

- `home`: current canonical statement and optional anchor;
- `scope`: files/packages/surfaces it governs;
- `principle`: why it exists;
- `decidability`: `deterministic`, `measurement`, or `judgment`;
- `check`: reference to a `#check` node;
- `exceptionPolicy`: none, pinpoint gap, ratchet, or decision;
- `reviewPrompt`: only for judgment rules.

`enforcement` should be derived from the referenced check's execution surface,
not manually duplicated.

### 8.2 Proposed check fields

A `#check` should declare:

- stable ID;
- implementation command/test/rule;
- input scope;
- execution surface: local, hook, CI, scheduled, or review;
- whether failure blocks admission;
- expected red-case fixture;
- health result separate from finding count;
- owner and last verified commit.

The governance harness should fail if a deterministic rule lacks a live check,
if the check is not invoked where enforcement claims, or if its red case no
longer fails.

### 8.3 Structured semantic review lane

Suitable initial judgment rules:

- Rule 1: abstraction before addition;
- canonical statement duplication/drift;
- module cohesion and interface depth;
- spec-first fidelity;
- property-test quality;
- node-model fit;
- unlabelled workaround detection.

Review input should be the changed files plus dependency impact, not the whole
repository on every commit. The reviewer emits strict JSON:

```json
{
  "ruleId": "...",
  "path": "...",
  "line": 123,
  "evidence": "...",
  "confidence": 0.91,
  "suggestedDisposition": "fix"
}
```

The receipt records:

- commit/diff/tree hash;
- pinned model and version;
- prompt hash;
- rule-set hash;
- changed-file and dependency-impact scope;
- findings with file/line/rule evidence;
- final disposition: fixed, gap, decision, or rejected with reason;
- human/agent reviewer identity and timestamp.

Initially, the raw stochastic verdict should remain advisory. The deterministic
meta-gate should enforce that:

- review ran when applicable;
- the receipt is schema-valid and fresh;
- every finding cites a valid rule and changed location;
- every finding has an explicit disposition;
- no accepted exception bypasses the gap/decision ledger.

After observing precision, selected categories may become blockers. Repeated
findings that can be recognized mechanically should graduate into harness
predicates with red cases and be removed from the semantic prompt.

This creates an organic progression:

```text
judgment concern
  -> reviewed finding
  -> named gap or decision
  -> repeated recognizable pattern
  -> deterministic predicate
  -> ratchet while debt exists
  -> hard gate
  -> gap removed
```

## 9. Recommended staged progression

### Stage 0 — stabilize the present transition

- Repair dependency installation after the harness move.
- Make package discovery ignore or diagnose non-package directories safely.
- Fix the test leaking writes into `tools/kb/.kb/nodes.jsonl`.
- Re-run clean-checkout `bun run verify` and preserve its receipt.

Exit condition: a clean frozen install followed by `verify`, non-UI tests, UI
tests, and docs check passes without changing the worktree.

### Stage 1 — close correctness and advertised-seam holes

- Validate action outputs centrally.
- Add fail-closed repository extension validation.
- Add bidirectional SDK/runtime type compatibility.
- Export one canonical core action contribution collection.

Exit condition: every declared action contract applies at runtime and every
repository extension is admitted before it can be loaded.

### Stage 2 — close deterministic enforcement bypasses

- Resolve and reject deep/relative cross-package imports.
- Canonicalize typecheck execution and source-extension coverage.

The current path is `packages/app/runtime/tests`. Because the generated file is

#### `app` versus `application` needs one crisp explanation

The hierarchy is mechanically coherent, but a reader cannot infer the
difference between `application/` and `app/` from the names alone.

The current dependency matrix implies:

  infrastructure and delivery surfaces;

State this distinction beside the package tree in one sentence. If the word
`app` continues to cause confusion, consider `composition/` or `delivery/` in a
separate behavior-preserving refactor. Do not rename it merely for aesthetics
while the distinction remains unnamed.

#### `test-kit` placement is coherent but surprising

`@kb/test-kit` sits under `app/`, while `@kb/render-tests` sits under
`test-support/`. This is intentional: `test-kit` directly composes runtime and
the JSONL storage adapter, so its dependency shape is an app-level composition
root despite its audience.

The folder is therefore truthful, but the package name suggests a different
layer. Either explain that exception next to the tree, rename the package to
reflect scenario/runtime composition, or deepen the runtime testing interface
until test-kit no longer reaches infrastructure and can naturally move to
`test-support/`.

#### `contract/contracts` is visually repetitive but not a design defect

The path `packages/contract/contracts` stutters. Renaming `@kb/contracts` would
create broad interface churn for little architectural gain. The singular
folder names the layer; the plural package names the collection of action,
storage, session, extension, and protocol contracts. Keep it unless contract
responsibilities are split for substantive reasons.

#### Workspace discovery still fails noisily on stale directories

`layerDirs()` and `packageDirs()` enumerate directories before validating their
manifests. An ignored stale directory under `packages/` previously caused an
ENOENT cascade rather than one clear unknown-layer/non-package diagnostic.
Failing closed is correct; improve the error locality by validating one layer
and package path before reading all manifests.

#### Graph-tool package recognition should be checked

After re-indexing, the codebase knowledge graph's architecture summary grouped
the nested workspace under one broad `packages` package even though symbol
paths remained searchable. This is an external-tool integration observation,
not a defect in the Bun/Nx workspace. Because repository guidance asks agents
to prefer the graph, verify that the indexer can represent
`packages/<layer>/<name>` as individual package nodes or provide it a generated
workspace manifest.
