## The contract as landed

The brief said gaps 1 and 2 are one gap seen from two stores. They are, and the
place that makes them one is the **store**:

```ts
// contracts/src/store.ts
readonly txTail: TxTail;
commitEffect(tx: StoreTx, record: TxRecord): Effect<StoreCommit, DomainError>;

// contracts/src/tx-log.ts
interface TxTail {                       // the durable sequence, the store's
  head(): number;
  isCurrent(): boolean;
  entries(): KbTx[];
  append(ops: StoreTx, record: TxRecord): KbTx;
  adopt(txs: readonly KbTx[]): void;
}
interface KbTxLog {                      // the session's view of it
  readonly head: number;
  refresh(): KbTx[];
  append(ops: StoreTx, at: string, origin?: string): KbTx;
  since(rev: number): KbTx[] | "snapshot-required";
  subscribe(fn: (tx: KbTx) => void): () => void;
}
interface TxRecord { readonly at: string; readonly origin?: string }
```

**Why the tail is on the store and not beside the log.** The brief offered a
choice (`appendTx`/`txSince`/`txHead` on `EffectStore`, or the store returning
the log as a capability). Neither, quite: the store returns the *tail*, and the
log is a separate object that views it. That fell out of one requirement — the
node write and the record have to be one critical section, and only the store
is inside the exclusion that makes them one. A log that owned its own file
would need its own lock, its own crash story and its own rev allocation: three
mechanisms for a sequence the store is already serialising.

That is also why `commitEffect` grew a **required** second parameter. A commit
nobody recorded is exactly the hole this wave closes — the transaction existed,
the store wrote it, and no reader could learn what it was — so `TxRecord` is
not optional and not defaulted. Its cost is one extra argument at every commit
site (~30, mechanical) and `txTail` on six test fakes.

**`MemoryTxLog` is gone, and so is its ring.** `StoreTxLog` holds no window.
The bounded in-process ring existed only because there was nothing durable to
read; keeping it beside a durable tail would have been two records of one
sequence, and the shorter one would have been the one answering
`snapshot-required` first. The name survives as `MemoryTxTail`, which is a
different thing on purpose: the tail of a store whose nodes are already
somewhere else — the browser replica (whose authority is the server) and test
fixtures. `isCurrent()` there is always true, because nothing in memory can
outlive the store it belongs to.

**Two ways a transaction enters the sequence, not two producers.**
`refresh()` adopts whatever the tail gained past head — that is how this
session's own commit is recorded (the store appended it) *and* how another
process's commit arrives, because the tail is shared. `append(ops, at, origin)`
records a transaction the store did **not** commit; there is exactly one such
case in the codebase (the saved-query virtual set) plus the un-logged-write
fallback. Both go through `TxTail.append`, so there is one writer.

`rev` is now the **store's** durable counter. `protocol.ts` said "a
monotonically increasing server counter" and now says what it is. The visible
consequence: a fresh root's first `hello` carries `rev 1`, not `rev 0`, because
seeding the `sys.*` nodes is a recorded transaction like any other. Three
existing assertions moved with a comment saying why.

## The two tails

| | tail | atomic with the node write? | rev allocation |
|---|---|---|---|
| JSONL | `.kb/tx.jsonl`, one canonical-JSON record per line | no — two files, one lock | under `.kb/nodes.jsonl.lock` |
| SQLite | `tx` table in `.kb/kb.sqlite` | **yes** — same `BEGIN IMMEDIATE` | inside that transaction |

```sql
CREATE TABLE tx (rev INTEGER PRIMARY KEY, at TEXT NOT NULL,
                 origin TEXT, ops TEXT NOT NULL, mark TEXT NOT NULL);
```

`ops` is `canonicalJson(StoreTx)` — the nodes' own bytes again, for the same
reason the `nodes` table stores a body rather than a column per field.
`schema_version` goes to `2`; `CREATE TABLE IF NOT EXISTS` is the whole
migration, and an existing database gains an empty tail, which is a state
`isCurrent()` already knows how to report. The tail's `rev` is its own counter,
not `meta.rev`: `meta.rev` also moves for a commit that records nothing (the
empty write `kb init --store sqlite` makes), and a sequence with holes cannot
be told from a compacted one.

`decodeStoredTx` joined `decodeStoredNode` in `@kb/model`, so "how a stored
transaction becomes a `KbTx`" is one function both tails call — the JSONL one
per line, the sqlite one per row. Its excess keys are *dropped*, the opposite
of the node decoder: a tail record's extra key is the adapter's own `mark`, and
a `KbTx` carrying it would put it on the wire in every frame.

Both tails **compact** at 2048 records down to 1024 — the bound the ring used
to impose, moved to the file so an unbounded sequence costs one rewrite instead
of unbounded disk. A reader further behind than that gets `snapshot-required`,
which the port already answered.

## The crash-order decision, and its test

**Nodes first, tail second.** It only matters for JSONL, where the two writes
are two files inside one lock. The order is not symmetric in cost:

- a tail that **lags** costs one snapshot, and is *detected*;
- a tail that **led** would hand every replica a frame for a write that never
  landed, and no later frame could take it back.

So the tail is allowed to be behind and never allowed to be ahead. Detection is
the half that makes that safe rather than merely reassuring. Every record
carries `mark`, the store's own durable commit mark as of that append —
`nodes.jsonl`'s size+mtime (the same string `JsonlStore.fingerprint` answers
with, now literally the same function), and sqlite's `meta.rev`. `mark` is
adapter-chosen because a uniform one cannot work: `PRAGMA data_version` is
meaningless across connections, so sqlite's fingerprint is not comparable after
a reopen while `meta.rev` is.

`TxTail.isCurrent()` compares the newest mark to the store's current one. When
it is false, `StoreTxLog` sets `floor = head + 1`, and `since(rev)` answers
`snapshot-required` for **every rev at or below head** — including a client
that is *at* head, which is the case a naive implementation gets wrong (it is
at head and still missing a change). The same detection covers a store written
by something that recorded nothing at all: a hand-edited `nodes.jsonl`, a
restore from backup, an older kb.

For the same reason the tail append is deliberately **not** `fsync`ed while the
node write is. Skipping the flush can only widen the lag, which is already
handled; paying an `fsync` per commit to shrink a window nothing falls into
would double the cost of every keystroke. That is a decision, not an oversight
— stated in `DESIGN.md`, in the code, and in the gap below.

The property is in the contract, not in an adapter's own file:

- `a store written without its tail reports itself behind` — commit, drop the
  newest record, reopen: `head()` is one behind, `isCurrent()` is false, and
  the nodes really are ahead (nothing was rolled back but the log).
- `a log over a stale tail refuses to serve frames` — `since(head)` and
  `since(0)` are both `snapshot-required`, and the next real append re-anchors
  the tail so frames from there on are servable again.

## `logContract` — the case list

`logContract(name, adapter)` in `@kb/test-kit`, beside `storeContract`, run by
both adapters. Ten properties:

1. an unwritten store has an empty tail that is current
2. a commit is recorded: one entry, the caller's `at` and `origin`
3. `rev` is monotonic and survives a reopen
4. a reopened log serves `since` from the durable tail
5. `since` beyond head is `snapshot-required`
6. an empty commit records nothing
7. an append that cannot be written leaves head unchanged
8. a store written without its tail reports itself behind
9. a log over a stale tail refuses to serve frames
10. a virtual transaction is recorded without touching the nodes

**Deviation from the brief, stated plainly.** The brief wanted `logContract`
written against a store factory. It is — `LogAdapter.makeStore` — but two of
those properties need a state only reachable *past* the port: a tail one record
behind its nodes, and a tail that refuses writes while still answering reads.
So `LogAdapter` carries one line for each, and the adapter supplies it:

| | `dropLastRecord` | `breakTail` |
|---|---|---|
| JSONL | a line off the end of `tx.jsonl` | `chmod 0444` |
| SQLite | a row out of the `tx` table | a `BEFORE INSERT … RAISE(ABORT)` trigger |

This is the same call `s1` made for the mid-write commit failure, in the
opposite direction: `s1` kept the injection in the adapter's package because
the *property* was adapter-specific; here the property is the port's and only
the injection is not, so the property stays in the contract and the injection
is a parameter. `storeContract` is untouched apart from the new commit
argument.

`@kb/tx-log`'s own test file was rewritten as `store-tx-log.property.test.ts`
over `MemoryTxTail` — the properties of the *view* (how head moves, who is
notified, where `since` refuses, and that a second log over the same tail opens
at its head and refreshes to what it gained).

## Migration

`kb store migrate --to` reads the source tail, commits the nodes, then
`adopt`s those records into the target with their revs intact. A migration
changes nothing a client can see, so it must not be the thing that forces every
client into a snapshot.

`adopt` **re-stamps** the store mark, because the marks in the source tail
describe a store that is about to be deleted; it runs after the node commit so
the mark it stamps is the target's settled one. A source with no tail — a store
written before tails existed — leaves the target the one record its own
migration commit made, which is the truthful answer: the whole graph arrived in
one transaction and nothing before it is known. The JSONL backend's file list
grew `tx.jsonl` and its `.bak`, so migrating away deletes them: selection is by
presence, and a tail describing a store that is gone is exactly what the
selector must never read.

Two tests in `store-selection.test.ts`: revs preserved across `jsonl → sqlite`
with `isCurrent()` true afterwards, and no tail left behind by the source.

## Gap 3: `withVirtual` stays

**Decision: keep it, and make the virtual set a logged transaction.** Dropping
it would mean materialising saved queries as stored nodes, which puts a
projection of `.kb/queries/*.edn` into `nodes.jsonl` — two sources of truth for
one thing, and the store gaining `sys.query.*` rows that a `kb` without the UI
would have to keep in sync.

`SavedQuerySet` (`app/server/src/saved-queries.ts`) owns the set:

- `adopt(nodes)` installs the first set without logging. The snapshot is taken
  after it, so logging it would spend a rev telling a client what it already
  has. Same pair the index has in `rebuild` / `applyTx`.
- `sync(nodes, at)` diffs against the current set, installs it, and appends the
  difference with `origin: "virtual"` (`VIRTUAL_ORIGIN` in the contract).

`.kb/queries/` is watched beside the store's own files. That needed a small
restructure first, in the same commit: the fs-event debounce is now
parameterised by the *program* it runs rather than by the session, and
`watchStore` became `watchScopes` over `{directory, names}` — so a
directory-shaped target (a listing that changes) and a file-shaped one (a name
replaced atomically) are one mechanism instead of two. `startUi` also ensures
`.kb/queries/` exists, because a directory that is not there cannot be watched
and a root that never saved a query would otherwise never notice its first one.

`SubscriptionHub` **lost its `virtual` argument**. It was the one surface where
a node reached a client without a transaction; it is now a pure log reader, as
its own doc comment already claimed.

**No `ui/**` change was needed for this.** The UI already applies `tx` frames
generically and already asks `since` on reconnect (`api/ws.ts`), so the virtual
frames and the durable rev both land on paths that exist. Two one-line UI edits
*were* needed for the port change, and are in commit 1: `BrowserStore` declares
`txTail = new MemoryTxTail()` (it is a replica — a second durable copy in the
browser would be a record with no authority claiming to be one) and
`session/runtime.ts` builds `new StoreTxLog(store.txTail)` where it built a
`MemoryTxLog`.

`ingestExternalWrite` also changed shape: it now `refresh()`es first, and the
node-set diff is the **fallback** for a write nobody recorded. It runs only when
the tail had nothing to say — otherwise a change the tail already explained
would be recorded twice, once as the writer authored it and once as this
session re-derived it. That was a real bug I hit: the first version double-
recorded every CLI write, and `tx-echo.test.ts` caught it.

## Both committed stores round-trip

Read-only opens of the two committed stores leave them byte-identical and
create no tail (a read appends nothing):

```
.kb/nodes.jsonl            f5087c565b3a69ad66ee05195ecec8a1  ->  unchanged
tools/kb/.kb/nodes.jsonl   a7d3290b322b9cc0f7cf52450615f910  ->  unchanged
```

Both were then copied to a scratch root and written through the CLI: each
produced a one-line `.kb/tx.jsonl` whose `mark` matched the new `nodes.jsonl`.
A `jsonl → sqlite → jsonl` round trip of the repo store (405 nodes) preserved
`rev 1` through both directions, re-stamped the mark each way (`"1"` in the
`tx` table, `211315:…` back on the file), and left exactly one store present.

`.kb/tx.jsonl` (plus `.lock`, `.tmp`, and `.bak` via the existing `*.bak` rule)
is gitignored in both `.gitignore` and `tools/kb/.gitignore`, asserted by
`gitignore-covers-derived`, and documented in `docs/backup-strategy.md` as
**state that is not even a backup concern** — derived-shaped, like
`nodes.jsonl.bak` and `kb.sqlite-wal`. The sqlite tail lives inside
`kb.sqlite`, which *is* committed, the same trade `nodes.jsonl` makes.

## Calls I made

- **The tail is on the store, and `commitEffect` takes a `TxRecord`.** The
  brief allowed a looser coupling (`appendTx` beside `commitEffect`). I took the
  tighter one because the atomicity the brief asked for is unreachable without
  it: with the append outside the commit, the JSONL tail cannot be inside the
  lock and rev allocation races between processes. Cost: ~30 mechanical call
  sites.
- **Commits 1–3 of the brief are one commit.** `EffectStore.txTail` cannot be
  half-implemented — the port is unsatisfied until both adapters have a tail,
  and neither adapter may import `@kb/tx-log` (infrastructure cannot import
  infrastructure), so "both adapters return an empty tail" was not a state that
  compiles. The remaining three commits are the brief's 4, 5 and 6.
- **The tail append is not `fsync`ed.** Argued above; filed as part of the
  JSONL atomicity gap.
- **`StoreTxLog` has no window.** The brief said the memory log "becomes the
  window over a durable tail". I deleted the window instead: with a durable tail
  that answers `entries()`, a second bounded copy of the same sequence is the
  mirror Rule 1 forbids, and `since` is a reconnect path, not a hot one.
- **The seed commit is logged.** It is a store transaction, so it gets a rev.
  Three tests asserting `rev: 0` on a fresh root now assert `rev: 1`.
- **`ingestExternalWrite` reads the tail before diffing.** Not in the brief, but
  it is the same "one producer" argument: another process's transaction is no
  longer lost, so re-deriving it is both wasteful and a second answer.
- **Two local test doubles in `ext-check`.** Its fixture needed a `TxTail` and a
  `KbTxLog`; it is an `extension` package and may not reach `@kb/tx-log`. I
  tried re-exporting them from `@kb/test-kit` (the sanctioned test edge) and the
  `public-surface` harness check correctly refused a cross-package re-export, so
  the fixture hand-rolls both — ~40 lines beside the fake store and fake index
  it already hand-rolls. Widening the import matrix for a test double would have
  cost more.
- **`queriesDir` exported from `@kb/workspace-fs`.** One line; the server needs
  the path it already owns.
- **`.kb/queries/` is created at server start.** A directory that does not exist
  cannot be watched.

because the defect is still exactly what it says.
