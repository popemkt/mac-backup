## The five `targetQuery`s as stored

All five are byte-identical to `graphSourceTargetQuery(kind)`; the migration
script reads them back from that function rather than restating them, so the
script cannot drift from the seed.

```
[:find ?id :where [?p :node/id "sys.graph.sources"] [?p :node/child ?c]
 [?p :node/child-order ?o] [?c :node/id ?id]
 [?c :f/sys.f.graph.source.kind ?k] [?k :node/id "sys.graph.kind.<KIND>"]]
```

| field | `<KIND>` |
|---|---|
| `sys.f.lens.color-by` | `category` |

## Where `kind` lives, and why

**A seeded ref field, `sys.f.graph.source.kind`, whose own four values are that
field's children** (`sys.graph.kind.{category,number,label,relationship}`).
Not `text`.

The brief left this open. `kind` takes one of exactly four values and never
anything else, which is the same closed set `fieldType` and `enforcement` have —
and k1 settled that shape: a closed value set is an option set, and an option
set is children. Choosing `text` would have left four magic strings in the store
that nothing declares, so a typo would be indistinguishable from a value and the
`kind` slot would get a free-text box instead of the ordinary ref picker.

The queries match on `:node/id`, not `:node/text`. Text is user-editable — the
option nodes are `sys.*` and write-guarded, but the query should not depend on
that guard to stay correct.

## First narrowing of the five source fields

Origin constrained only `renderer`; the five source fields were **unrestricted**
(`allowedRefIdsOf → null`). They now resolve to 3 / 3 / 1 / 3 candidates. Two
consequences, both checked rather than assumed:

- **`graph-lens.ts` reads a stored value the picker would not offer, without
  throwing.** A user field is stored as `{t:"str", v:"prop:<id>"}`
  (`sourceValue` → `graphSourceId` returns null for a `prop:` key), so it is not
  a ref at all and no constraint applies; `parsePerspective`'s `source()` reads
  it through the `strProp` fallback. Live proof: `lens.all-mentions` in **both**
  committed stores still holds pre-node strings
  (`cluster-by:"parent"`, `renderer:"force2d"`, `edge-kinds:["mention","child"]`)
  and parses unchanged. Pinned by two cases in `graph-sources.test.ts`.
- **`graph-bindings.ts` is unaffected**, and deliberately: the graph page's own
  option lists come from `graphBindingOptions(nodes, kind)`, which enumerates
  seeded options *plus discovered user fields*. The narrowed `targetQuery`
  governs the generic inline field editor's picker. These are different
  questions — "what may this field name" (data) versus "what will this panel
  offer" (display, which here deliberately offers more).

One asymmetry worth recording rather than papering over: `perspectiveProps`
writes `sys.graph.source.none` (a **category** option, "No grouping") into
`lens.edge-kinds` as the "explicitly no edge kinds" sentinel, because an absent
prop means "unset" and falls back to `DEFAULT_EDGE_KINDS`. The narrowed picker
will not offer it there, which is right — a user should not pick "No grouping"
from a relationships list; unchecking every box in the graph panel is what
produces it. Read back, `parsePerspective` filters it out and yields `[]`,
i.e. behaviour unchanged. Asserted in `graph-sources.test.ts`
("reads the `none` edge-kinds sentinel back as no edge kinds"). Not filed as a
gap: the encoding is intentional and the two surfaces agree on its meaning.

## Migration script

`docs/kb/waves/2026-09-09/reports/g1-migration.sh`, both stores, CLI only,
`--force` only on `sys.*` nodes, every step guarded.

It starts each store with one harmless `kb query` so `ensureSystemSeed` runs
first: that pass seeds `sys.graph.sources` with its ten children *declared*
(so no adoption is needed for them), `adoptSeedChildren` adopts the five
orphaned renderer options, and the fill-absent-props pass writes the ten `kind`
refs and the five `targetQuery`s — none of which existed on those nodes before.
So the script's own remaining work is exactly what that pass will never do:
remove props that already hold a value (15 kind refs, one `targetTag`) and
delete the two tag nodes. The `kind` and `targetQuery` steps therefore print
`· already done:` in practice, and are kept because they state the intended end
state for a store where seeding did not apply.

`kb field target-query` has no `--force` and all five fields are `sys.*`
(verified: `error [forbidden] sys.* nodes are write-protected`), so those steps
use `kb set <field> sys.f.targetQuery … --type str --force` — the same plan
through the same validator, with admission granted.

Second run is a clean no-op:

  · already done: graph-renderer

## Calls I made

- **`kind` as a ref into a four-child option set, not `text`.** Reasoning above.
- **Kind option ids and the field→kind map live in `graph-schema.ts`, not
  `SYSTEM_IDS`.** Precedent: the renderer and source option ids already live
  there. `SYSTEM_IDS` gets the two *structural* ids (a list root, a field),
  which is what it already holds. `graph-schema.ts` now imports `SYSTEM_IDS`;
  no cycle (`model.ts` imports neither).
- **Collapsed the field→kind duplicate rather than adding a second copy.**
  The seed needs "size-by is a number channel" and the graph panel already had
  it in `CHANNELS`. Adding it to the seed as well would be the mirror Rule 1
  forbids, so `GRAPH_SOURCE_FIELD_KINDS` is now the one declaration and
  `CHANNELS` dropped its `kind` column. `graph-mappings.tsx` looks options up
  **by field id** (`sourceOptionsByField`, memoized per kind) instead of by
  kind, because "which options does this field accept" is the question every
  call site there actually has.
- **Collapsed `refQueryField` in the seed.** `onto.extends` and the five lens
  fields are the same thing — a ref field whose targets are one EDN query's
  rows — and were two inline copies of that object literal.
- **New test file rather than editing a shared one.** The natural home for
  "these five fields resolve to these rows" is
  `packages/app/server/tests/field-target.test.ts`, but `app/server` is g6's
  zone this batch. `packages/app/ui/src/lib/graph-sources.test.ts` is new, in my
  zone, and tests the binding the browser picker actually runs.
- **`GraphMappings` was refactored, not exempted.** My first pass pushed it from
  120 to 121 lines, which registers a *new* `max-lines-per-function` site and
  fails the frozen ratchet (`count changed from 35 to 36`). Hoisting the option
  lookup to module scope put it back under the line and removed the last copy of
  the kind map at the same time. The baseline file was not touched.
- **Two prose updates.** `DESIGN-UI.md` → "Field-based graph perspectives" said
  new values "reference … seeded graph-source nodes; renderer choices reference
  graph-renderer nodes", which is now false. `DESIGN.md` → "Kinds, roles and
  options" gained one bullet for the shape this wave is the second instance of:
  *one option list, several fields, each selecting from it by query* — the case
  where parenting alone cannot express the set because a node has one parent.
  That is a sharpening of the existing rule, not a new carrier: `targetQuery` is
  the general form and parenting is its single-field sugar.
