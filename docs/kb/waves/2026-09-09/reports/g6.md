### 1 — palette perf test

`palette-index.test.ts` asserted `openMs < 50` and `keyMs < 10`. The claim
worth gating is algorithmic: a keystroke is one linear substring pass over the
prebuilt haystack, not an index rebuild and not a second 50k subsequence scan.
That is now a ratio against a baseline pass timed on the same host in the same
run (`PASS_BUDGET = 8`), so load slows both sides alike. Measured here:
baseline 0.83 ms, keystroke 2.44 ms — **2.95 passes** against a budget of 8; a
rebuild would land near 50. Absolute timings print as an observation table, the
way `storeBenchmark` records its phases, and are asserted by nobody.

### 5 — the merge driver

Resolution rules live in `mergeNodeSets` (`@kb/model`), tried in order:

1. both sides agree, deletions included → take it;
2. one side still equals base → the other side wins, so a deletion of a node
   the other side left alone is honoured;
3. both changed and both still have it → newer `updatedAt`;
4. anything left is reported, not guessed: `deleted-and-modified` (one side
   deleted what the other edited) and `modified-both-same-stamp`.

A conflict still produces a complete, loadable file — the surviving version is
kept and the ids are named on stderr — so the store is never left as text with
markers in it.

`packages/app/cli/src/bin/merge-jsonl.ts` is the git boundary and nothing else.
`.gitattributes` (new, repo root) routes both `.kb/nodes.jsonl` and
`tools/kb/.kb/nodes.jsonl` through it.

**Git config is per clone and is not versioned**, so it has to be registered
once per clone, from the repo root — documented in `tools/kb/AGENTS.md` beside
the other per-clone setup:

```bash
git config merge.kb-jsonl.name "kb node store (three-way by node id)"
git config merge.kb-jsonl.driver \
  "bun tools/kb/packages/app/cli/src/bin/merge-jsonl.ts %O %A %B %P"
```

Without it git falls back to today's text merge — noisy, never wrong about
content. **I did not run it in this worktree**; the coordinator should, per
clone.

No third serializer. `canonicalJsonl` — sort by id, canonical JSON per line,
trailing newline — existed twice, inline in `JsonlStore.commitEffect` and
copied into the test harness. It now lives once in `@kb/model` and both callers
read it, which is what let the driver reuse the store's exact bytes. Two
consequences: `harness/public-surface` forbids a barrel re-exporting another
package's symbols, so `@kb/test-kit` no longer re-exports it and its two
consumers import from `@kb/model`; that left `@kb/test-kit` unused in
`@kb/ext-check`, so the devDependency is gone (`bun.lock`, one line).

Cases covered, over node sets in `@kb/model` (10 tests) and through **real
`git merge` in a temp repo** in `@kb/cli` (5 tests): the tail-collision append
that git cannot resolve; a side equal to base yielding; an honoured deletion;
both-changed with ours newer and with theirs newer; identical edits on both
sides; both sides deleting; delete-racing-edit stopping the merge and naming
the id; only-one-side-changed coming out byte-identical to that side's file;
and canonical output (sorted, one line each, no spaces, trailing newline).

### 6 — action output schemas

`parseActionInput` is now `parseBySchema`, because that is what it always was —
a value and an action schema. Input on the way in and result on the way out are
the same operation, so they use the same parser rather than a second one
written to match it. What differs is whose fault a mismatch is, and that stays
at the call site: an input mismatch keeps `invalid_input`; an output mismatch is
kb's own broken contract and becomes an `internal` failure naming the action and
carrying the schema's issues, on both handler kinds, never a throw across the
boundary.

The receipt carries the parsed value. A check whose result is discarded is not
a check.

Tests: an invalid output from an Effect-native handler and from a Promise
handler, each landing as `internal`, and a declared-shape receipt for a handler
that returns more than it promised. Red-checked — all three fail with the parse
removed. No existing action's output changed shape.

### 7 — store staleness (half)

**What the fingerprint site looked like.** `EffectStore.fingerprint` exists
(s1) and `reloadEffect`/`persistEffect` already compare it rather than
`stat` — the gap's `current` was written after that landed. The three adapters:

- `SqliteStore` — `rev` plus sqlite's `data_version`. Content-derived; already
  satisfies the gap's first window, and its own comment says so.
- `BrowserStore` — a generation counter. Single-threaded, so exact.
- `JsonlStore` — `${size}:${mtimeMs}`. This is the one that does not.

So the gap's `closes` is satisfied by two of three adapters, and what was left
split in two.

**Closed: the persist race.** A store commits by merging — it reads current
state inside its own exclusion, applies the tx, writes the result. Persist
caught up *before* that, outside the lock, so a write landing in between was
absorbed into the file the commit produced while the index only got the local
delta, and the fingerprint taken afterwards stamped that index as current. The
session then stayed quietly behind its own store until the next write it
noticed.

`commitEffect` now returns a `StoreCommit` — the fingerprint it merged into
and the one it left. That is the gap's own second option, and the store is the
only party that can answer: the merged-into state is known inside the lock and
nowhere else. Persist compares. Merged into what this session had read → the
local delta is the whole difference, `applyTx` stands. Anything else → rebuild
from the store instead of stamping on a guess. Null still compares equal to
nothing, so a store that cannot say costs a reload and never a stale index.

Test: a store that lets a foreign write land between persist's catch-up and its
own merge; the index ends up with both nodes and the reload right after finds
nothing to do. Red-checked.

**Left open: JSONL's fingerprint itself.** Size plus mtime cannot see an
external write in the same millisecond tick that keeps the byte count
identical. Closing it means hashing the file on the one path whose purpose is
to answer "did it change?" *without* reading it — a real cost on every
pre-action staleness check, for a race needing a second process writing the
same store within one tick at an identical length. Recorded rather than paid.

Port change reached three adapters, five test doubles, and `@kb/contracts`. One
of those doubles held nodes its own `loadEffect` denied, which is not a store;
it is now the smallest honest in-memory one.

### 8 — subscription fan-out (half)

**Closed: one evaluation per distinct query per tx.** `publish` looped clients,
then that client's subscriptions, and ran the full query for each. Evaluation is
now keyed by query string. The decision stays per subscription — each keeps its
own last-seen hash, because two clients on one query can be at different points
in it.

Test: three subscriptions over two queries across two clients, one edit, two
datalog runs (three without the sharing), and the shared answer still reaching
both subscribers.

**Left open: the read-set gate — and the blocker is not the IR.** `@kb/query`'s
IR *does* expose what a compiled query reads: `PatternClause.attr`,
`ReachClause.edge`, the children projection. The other side is the problem. A
`StoreTx` carries whole nodes *as they are after the write*, so a removed prop
and every attribute of a deleted node are simply absent from it. A gate built
on that write set would silently drop exactly those changes. It needs the tx log
to carry before-images (or the store to report a per-tx attribute set), plus a
fallback that always re-runs an `IrRaw` query, which exposes no read set at all.
`closes` now says that.
