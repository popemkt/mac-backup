## The registry's shape

**One table, two columns**, in `components/outline/field-value.tsx`:

```ts
interface FieldEditor {
  readonly icon: Icon;                                  // FieldRow's type glyph
  readonly Editor: (props: FieldEditorProps) => React.ReactNode;
}
const FIELD_EDITORS: Record<FieldType, FieldEditor>
```

| type | icon | editor |
|---|---|---|
| `text` | `TextTIcon` | `textualEditor({ underline: false, isEmpty: isBlankScalar, parse: str })` |
| `url` | `TextTIcon` | `textualEditor({ underline: **true**, isEmpty: isBlankScalar, parse: str })` |
| `number` | `HashIcon` | `textualEditor({ underline: false, isEmpty: t !== "num", parse: num-or-reject })` |
| `date` | `CalendarBlankIcon` | `DateEditor` |
| `checkbox` | `ToggleRightIcon` | `BooleanEditor` |
| `ref` | `LinkSimpleIcon` | `RefFieldEditor` |

Display and edit are **one component per type**, not two, because every editor
here *is* its own display until it is clicked — that is what makes an inline
field feel like text rather than a form control. The coercion the brief asked
for as a third member is a column of the textual family instead
(`TextualSpec.parse`), which is where it actually varies: `text`, `url` and
`number` share one editor and differ only by `underline`, `isEmpty` and
`parse`. Their `show` is identical (`value.t === "str" ? value.v :
String(value.v)`), so it is not a column — the old `number` case wrote
`value.t === "num" ? String(value.v) : String(value.v)`, both arms the same.

### The second, narrower table

`sys.f.color` is a text field edited as swatches. That is not a *type* special
case, so it is not an `if` inside a type's row either:

```ts
const FIELD_ID_EDITORS: Readonly<Record<string, FieldEditor>> = {
  [SYSTEM_IDS.colorField]: { icon: PaletteIcon, Editor: ColorEditor },
};
function editorFor(fieldType: FieldType, fieldId?: string): FieldEditor  // id wins over type
```

One row replaces three `if (fieldId === SYSTEM_IDS.colorField)` — one in
`PropValueEditor`, one in `EmptyTypedEditor`, one in `FieldRow`'s icon.
`FieldRow` renders `<FieldTypeIcon>` rather than looking a row up itself, so a
row's glyph and its editor cannot come from different rows. (`editorFor` stayed
module-private for that reason: `react/only-export-components` is an error
here, and a component is the honest export anyway.)

### The lib-side table it sits on

`lib/field-type.ts` had **four** switches over the same union —
`expectedPropKind`, `isValueMismatch`, `emptyValueForType`,
`fieldTypeIconKind`. Now one row per type:

```ts
interface FieldTypeSpec { wireKind; accepts: readonly PropValue["t"][]; empty: PropValue }
const FIELD_TYPE_SPEC: Record<FieldType, FieldTypeSpec>
```

`fieldTypeIconKind` is gone entirely — the icon is the registry's column, so
`FIELD_ICON: Record<PropValue["t"], Icon>` and `resolveIconKind` in
`field-row.tsx` went with it. Every `default:` went too, so a seventh field
type now fails the build instead of silently rendering as text.

### Two dead seams deleted

- `FieldRowProps.fieldType: FieldType | PropValue["t"]` — no caller ever passed
  a wire kind. `resolveIconKind` existed only to fold that half back in.
- `RefEditor`'s resolved-branch label was `(target?.text ?? display) ||
  target.text || "​"`, in which `display` is unreachable when `target`
  exists. A resolved target's own text is the label; `display` is only ever the
  fallback for an unresolved id.

### One behaviour deliberately kept, and it looks wrong

`url` shows the **text** glyph, because `fieldTypeIconKind("url")` returned
`"str"`. That is preserved verbatim — a refactor commit does not change what
the screen shows. It is now a cell rather than a fall-through, so giving `url`
`LinkSimpleIcon` is a one-word change whenever someone decides it should have
one. Flagging it rather than fixing it under a `refactor:` label.

## The other four values

- **`useRefCandidates`** (`lib/use-ref-candidates.ts`, 112 lines) — candidate
  search *and* its keyboard navigation. Four keys through g4's
  `lib/keychord` table, not a second matcher; the two arrow rows carry
  `candidates.length > 0` as a row condition (`accepts`), which is exactly what
  the old chain's inline guard was. The highlight is anchored to the query it
  was chosen under (`{ query, index }` in one state), so a new query returns it
  to the top without an effect — and that is what lets the query be a **prop**,
  so `node-content`'s `[[` autocomplete can adopt the hook later without owning
  its own index. It reads `fuzzyNodeCandidates`; there is still exactly one
  candidate source.
  `RefEditor` is now four named states — `ResolvedRefRow`, `UnresolvedRefChip`,
  `EmptyRefSlot`, `RefSearch` — and holds nothing but `open`.
- **`bulletAppearance`** (`lib/bullet-mode.ts`) → `{ kind, shape, glyph,
  isSys, isRef, hasChildren, collapsed, childCount, collapsible, showHalo,
  showCount, tinted, haloFill, dotFill, strokeColor, ringColor, title,
  ariaLabel }`. `BulletShape = "supertag" | "query" | "ref-ring" | "glyph" |
  "dot"` is the union the nested JSX ternary encoded by position, and naming it
  is what makes its two load-bearing rungs legible: a supertag and a query node
  keep their own shape *on a reference row*, while a glyph kind gives way to
  the dashed ring. `Bullet` renders `BULLET_SHAPES[shape]`, a `Record` over
  that union.
  `resolveBulletMode` was **deleted rather than kept beside it** — it copied
  four input fields and called `resolveBulletKind`, i.e. it was the same value
  half-built. Its one test now asserts the same flags through
  `bulletAppearance` (the only edit to a pre-existing test in this wave).
  `resolveBulletKind` stays; appearance builds on it, as the brief asked.
- **`resolveRowChrome`** (`lib/row-chrome.ts`, 86 lines) → `{ bulletIsRef,
  hasFields, showsQueryResults, showsChildren, hasFrameRows, isExpandable,
  showToolbar, projected, showsCreateChild, showsChildContainer }`. The flags'
  *dependencies* are why it is one function rather than ten accessors:
  `isExpandable` is derived from the render gates, so the bullet's toggle
  promise cannot exceed what the gates deliver. `NodeBlock` reads `chrome.*`
  and decides nothing.
- **Table columns and sort** (`lib/view-config.ts`).
  `mergeColumns(explicitColumns(…), () => derivedColumns(…))` — the precedence
  is that one function's body now, not statement order. `explicitColumns`
  returns `null` (not `[]`) when the frame names nothing, which is what keeps
  "the frame named only hidden fields" showing no columns instead of falling
  back to derivation; the old code re-checked `display.length === 0` twice to
  say the same thing. The asymmetry between the sources is stated where it
  happens: a **named** `sys.` field is kept (naming one is the decision), a
  **derived** one is not.
  The sort is `composeComparators(specs.map(compareByField))` over
  `SORT_KEY: Record<PropValue["t"], (value, nodes) => number | string>`, one
  row per value type. `__name__` stopped being a branch: `PSEUDO_FIELDS`
  resolves it to a `PropValue` like any other key, so one ordering rule serves
  both and "the name is never missing" is no longer a special case. Two rules
  that were previously only visible by reading the whole comparator are now
  named: a missing value sorts last *before* the direction applies (so
  descending puts it first), and two values of *different* types compare as
  raw strings rather than through either one's key — a ref mixed with a string
  has no shared ordering, and reaching for the ref's resolved text there would
  be inventing one.

### One blind spot, stated in the file that has it

React's `onChange` **does not fire for an `<input>` under happy-dom** (its
`onInput` does; a probe confirmed the synthetic change event never arrives, for
both controlled and native-setter writes). Two writes are only reachable by
typing into a real input — the native date picker's pick, and the ref picker's
"commit the raw query when nothing matched" fallback. Those two are pinned by
what the editor *offers* (the seeded `input[type=date]`, the search box and its
single placeholder) rather than by the value written, and the file's header says
so. Everything reachable through click, focus, blur and keydown is asserted for
real, including all three textual `parse` paths and the swatch write.

This is a harness limitation worth a gap of its own if anyone else trips on it;
I did not file one, because it is one line of context in one file and filing it
as a repo-wide `#gap` would overstate it. Flagging for the coordinator's call.

## Calls I made

- **The registry is two tables, not one.** A field's editor is chosen by its
  declared type, *overridden* by its field id. Collapsing those into one table
  would have meant keying by `string` and losing the exhaustiveness check that
  makes a missing field type a build error. Two tables with one stated
  precedence (`editorFor`) is a bridge, not a mirror.
- **Display and edit did not become separate components.** The brief's `Editor`
  carries "the display component, the edit component and the coercion". In this
  code they are one component per type, and splitting them would have invented
  a seam the behaviour does not have. The coercion became a column where it
  genuinely varies (the textual family).
- **`resolveBulletMode` deleted rather than kept as the layer under
  `bulletAppearance`.** Keeping it would have left an exported function whose
  only caller was its own test — a dead seam, which Rule 1 calls a duplicate.
  Its assertions moved to `bulletAppearance` unchanged. This is the one
  pre-existing test file I edited.
- **`FieldRow` kept its `icon` prop.** Preferences rows pass a glyph that is
  not any field type's (`FunnelIcon`, `TextAaIcon`, a theme glyph). That is an
  override of the registry's answer, not a competing mechanism, and it is
  documented as one.
- **The hook takes `query` as a prop rather than owning it.** The `[[`
  autocomplete derives its query from node text and cannot hand that to a hook
  that owns query state. Making the query an input is what keeps one hook
  serving both — the alternative was a second candidate controller, which the
  brief explicitly rules out.
- **`lib/use-ref-candidates.ts`, not inside `lib/refs.ts`.** `refs.ts` is pure
  and is read by non-React tests; adding `react` to it changes what the module
  is. The hook sits beside it in the same zone. (`lib/router.ts` already holds a
  hook, so this is not a new precedent.)
- **`SORT_KEY` gives each type a key instead of a comparator.** A
  `Record<PropValue["t"], (a: PropValue, b: PropValue) => number>` cannot narrow
  its arguments to the variant its key implies, and `strict-boolean-expressions`
  plus `no-unsafe-type-assertion` (both `error`) leave no clean way to write it.
  A key extractor needs no narrowing and reads better anyway.
- **`resolveTableColumns`'s `mergeColumns` takes a thunk.** Derivation walks
  every projected row's tags; a frame that names its columns should not pay for
  it. `explicit ?? derived()` with a lazy second argument.
- **Did not file a gap for the happy-dom `onChange` limitation.** See above —
  coordinator's call.
