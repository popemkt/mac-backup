## The schema

```sql
CREATE TABLE nodes (id TEXT PRIMARY KEY, body TEXT NOT NULL);
CREATE TABLE meta  (key TEXT PRIMARY KEY, value TEXT);   -- schema_version, rev
```

`body` is the same `canonicalJson(node)` string the JSONL writes — one row per
node instead of one line per node. Deliberately not a column per field: a
node's bytes are the only thing the store promises to give back, and DDL
mirroring the node schema would be a second, partial copy of the model that has
to grow every time the model does. `id` is the primary key because it is the
identity the model already has.

`PRAGMA journal_mode = WAL`, `synchronous = NORMAL`, `busy_timeout = 15000` —
the busy timeout is deliberately the same 15s ceiling `write-lock.ts` already
spends waiting, so a contended commit behaves the same on both adapters rather
than failing fast on one and spinning on the other. A commit is one
`BEGIN IMMEDIATE … COMMIT` covering deletes, upserts and the `rev` bump; there
is no `.lock` file, because sqlite's write lock already is one and a second
mechanism beside it would be the one that lies.

**The store owns its connection**, opened lazily and kept. The caller cannot:
`EffectStore` is built once per session and handed to layers, actions and the
watcher as a plain value, and none of them has a scope to hang a connection
off — `KbContext` is not scoped. The half that matters for correctness is that
a *read* never creates the file (`SqliteConnection.peek`): a store that was only
loaded from must not conjure `kb.sqlite`, or selection would see two stores
under one root. There is a test for exactly that.

## The fingerprint argument

`${rev}:${PRAGMA data_version}`.

- `rev` is a counter this store bumps **inside** the commit transaction, so it
  moves even when a commit's content is byte-identical to what was already
  there. That is precisely the case `JsonlStore`'s size+mtime cannot see
  (GAP `01M1PK5NYA7ZG3XC0H0YRYRVZE`). It is read from the table rather than
  cached in memory, so it also sees other connections' commits.
- `data_version` moves when *another connection* commits. It catches a writer
  that bypassed `rev` altogether — a `VACUUM`, a hand-run `sqlite3`, a schema
  change. Both halves have their own test.
- Null when the file does not exist, so an unopened store compares equal to
  nothing and the session reloads.

**This closes the blind spot for sqlite only.** GAP `01M1PK5NYA7ZG3XC0H0YRYRVZE`
stays open, because it is still true of the JSONL adapter, which is still what
an unconfigured root gets. `contracts/src/store.ts`'s doc comment was updated
where it had guessed wrong ("a future SQLite store would use its own change
counter" → what it actually uses).

## The contract, and what it now says

`storeContract(name, makeStore)` moved into `@kb/test-kit` and is a list of
named properties a `describe` block registers against whichever factory an
adapter hands it. Both adapters run all seven:

1. an unwritten store loads empty and has no fingerprint;
2. write-then-read round-trips any generated node set (the old fast-check
   property, moved verbatim, 100 runs);
3. a commit merges — upserts overwrite, deletes remove;
4. the fingerprint is stable across pure loads and moves when the content does;
5. a second instance over the same files is seen, and moves the fingerprint;
6. concurrent commits serialize — neither writer's nodes are lost, and a loser
   fails with a `DomainError` rather than silently;
7. a commit that cannot be written fails with a `DomainError` and leaves no
   store behind.

**Deviation from the brief, stated plainly.** The brief asked the contract to
carry "commit is atomic under a failure injected mid-write (sqlite: a second
connection holding a write lock)". A held write lock is not a port-generic
injection: `storeContract`'s signature is `(name, makeStore)`, and the two
adapters reach that state by different mechanisms with different observable
timings (JSONL spins on an advisory lock, sqlite blocks in the driver). So the
contract carries the generic form (property 7 — a write the platform refuses)
plus property 6, and the mid-write case lives in the sqlite adapter's own test
where it can be injected honestly: a `BEFORE INSERT` trigger that `RAISE(ABORT)`s
on the second of two upserts, after the first has already been written inside
the transaction. The commit fails with a `DomainError`, the rollback is real,
and the store is unchanged.

The JSONL package keeps its adapter-specific coverage; note that its lock-file,
`.bak` and line-numbering tests already lived in `runtime/tests/persistence.test.ts`
rather than in the package, and were left there.

`storeBenchmark(name, makeStore)` joined the contract in `@kb/test-kit` for the
same reason. Its phases are port-level, so the two adapters produce two columns
of one table. **The JSONL benchmark's read-versus-decode split was dropped**: it
measured two halves of `JsonlStore.loadEffect`, which the port does not have.
`decodeNodes` was un-exported with it rather than left as a dead seam;
`briefs/p1-persistence.md` can measure the adapter's internals directly when it
picks incremental reading up.

## Benchmark — 50k nodes, same machine, same run

`bun test packages/infrastructure/store-{jsonl,sqlite}/tests/benchmark.test.ts`.
Not asserted on; measured gates still belong to Phase 4.

| phase | JsonlStore (ms) | SqliteStore (ms) |
|---|---:|---:|
| initial commit | 52.3 | 149.6 |
| load | 86.2 | 69.0 |
| datom build | 198.5 | 160.8 |
| query | 35.5 | 36.1 |
| `kb set`-shaped commit | 121.7 | **4.2** |
| interactive edit | 178.5 | **51.1** |

The one large win is the incremental commit: JSONL rewrites the whole file
under a lock, sqlite writes the rows that changed. Bulk load is a wash, and
`datom build` and `query` are identical work on both — which is the shape of
the first gap below.

## Migration, proven both ways on a copy of the live `.kb/`

`.kb/` was copied to a scratch dir (never migrated in place):

```
$ kb --root <scratch> store migrate --to sqlite
migrated 341 nodes from jsonl to sqlite (…/.kb/kb.sqlite)
$ ls .kb/         → kb.sqlite, kb.sqlite-wal, kb.sqlite-shm, queries/, views/
$ kb --root <scratch> search "drift" --json
{"status":"succeeded","id":"graph.search","output":{"rows":[["01M1M071DD75C6RZAFDPGTH46Z","Drift markers"]]}}
$ kb --root <scratch> store migrate --to jsonl
migrated 341 nodes from sqlite to jsonl (…/.kb/nodes.jsonl)
$ ls .kb/         → nodes.jsonl, queries/, views/   (no kb.sqlite*)
```

`sha256(nodes.jsonl)` before: `551c5e83c07ea9040f7ece0c70e686a982d1b4b3ce2d4b0d2638dc148f2c6244`,
341 lines. After the round trip: **identical**. Both adapters write the same
canonical bytes, so a round trip is a no-op on the file — which is the strongest
statement the shared decoder buys.

`kb init --store sqlite` on a fresh root creates `kb.sqlite`, seeds 23 example
nodes into it, leaves no `nodes.jsonl`, and `kb add` / `kb search` work against
it (`meta.rev` = 6, 99 rows). `kb init --store duckdb` exits 2 with a usage
message. A root with both files present refuses every command with the
`conflict` naming both paths.

## Decisions worth reviewing

**`store.migrate` is a CLI command, not an action.** The brief allowed either
with a reason. `@kb/operations` is `scope:shared` in the `application` layer, so
it may import neither `bun:`/`node:` nor an infrastructure package. Migration is
*defined* by constructing both concrete adapters and deleting their files;
written against `EffectStore` alone it cannot name a single one of those. The
one place entitled to know two adapters exist is the composition root, so
`migrateStore` lives beside `selectStore` in `@kb/runtime` and
`kb store migrate --to <jsonl|sqlite>` is a thin surface over it.

**`conflict`, not `invalid_state`.** The brief specified
`domainError("invalid_state", …)` for the both-present case. `DomainError` has
no `invalid_state`; its codes are a subset of `FailureCode`, and adding one
would widen the receipt mapping and the wire protocol for a single call site.
`conflict` is what two stores claiming one root actually are. Recorded here
rather than silently.

**The backend table has one entry per adapter and no `instanceof`.** Selection,
`kb init --store` and migration all read `BACKENDS` in
`runtime/src/store-selection.ts`. A small `backend<S extends EffectStore>()`
helper erases each adapter's concrete type while its `release` callback still
sees it, so sqlite's `close()` is reachable without a cast or a branch, and
JSONL's release is simply absent.

**`kbAction` lost its `allowCreateRoot` fork.** `kb init` is the one command
that runs *before* a session could exist — it creates the root and picks the
store the open will then select — so it uses `cliAction` and opens the session
itself, exactly as `kb ext-sdk --write` already did. `allowCreateRoot` had no
other caller and is gone: one fewer boolean parameter forking a shared helper.

**`EffectStore.watchPaths`** rather than a second `if` in the server. The server
now asks the store what to watch and can watch more than one path
(`kb.sqlite` + `-wal`), falling back to `.kb/` for any path not yet created.

## Files touched that s1 does not own

Three, each forced by the port change and each a single line — named here for
the coordinator rather than worked around:

- `packages/app/ui/src/session/browser-store.ts` — `BrowserStore implements
  EffectStore`, so it needs `watchPaths` (`[]`: the server pushes it its news).
  Overlaps u1/u2's package but not their files.
- `packages/app/runtime/tests/{persistence,native-actions}.test.ts` — three
  inline `EffectStore` literals needed the same field.
- `harness/tests/gitignore-covers-derived.test.ts` + repo `.gitignore` — two
  entries so `kb.sqlite-wal` / `-shm` are covered like the JSONL sidecars.

`harness/lint-warn-baseline.json` changed only via `bun run harness:snapshot`,
never by hand: one knip entry disappeared (store-jsonl's `@kb/test-kit`
devDependency became a real edge).
