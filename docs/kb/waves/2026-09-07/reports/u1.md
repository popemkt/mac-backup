## What landed

`ARCHITECTURE.md`'s "Import / ownership rules" table is now `UI_ALLOWS` in
`tools/kb/harness/src/constraints.ts`, beside the package matrix and under the
same shape: one `Record<zone, readonly zone[]>`, one `uiZoneOf(file)` that
knows the path→zone mapping, one specifier rule (`UI_SPECIFIER_ALLOWS`) for
the `ds` seam. `tools/kb/harness/src/ui-imports.ts` resolves relative and

`import-graph.ts`'s file walk and `oxc-parser` module record rather than
parsing imports a second time. `tools/kb/harness/tests/ui-boundaries.test.ts`
applies it, and is part of `bun run harness` / `bun run verify`.

## Ambiguities, and how they were read

Stricter than the table:

- **`catalog` is inside the matrix, not exempt.** The brief grouped `catalog/`
  with test files as exempt from the surface rows; that would have made
  `catalog`'s row dead. It has a real row instead (stories may read
  components, primitives, `lib`, `fixtures`), so the table's "must not: stores
  mutations except fixtures" is actually enforced. Observably the same for
  stories; strictly more checked.
- **Test files are exempt from `UI_ALLOWS`, never from `UI_SPECIFIER_ALLOWS`.**
  71 further breaches sit in `*.test.ts(x)` files; a test reaches for what it
  drives, and fencing them would fence the tests rather than the product. The
  `ds` rule still applies, which is why `session/runtime.test.ts` carries a
  marker.
- **`ds`'s row is itself alone.** The table gave it `@kb/query` and a "must
  not import components"; the stricter reading is that nothing else is allowed
  either, and it holds — `ds/index.ts` imports only `@kb/query`.
- **`lib`'s "types" is `lib/types.ts`, not `src/types/`.** `src/types/` holds
  ambient declarations, imports nothing and is imported by nothing, so its row
  is itself and no other row names it.
- **`primitives` is a path set, not a name list.** `ARCHITECTURE.md` listed the
  primitives by exported symbol (`TagChip`, `NodeRow`, …), which no check can
  match to a file. `UI_PRIMITIVES` is prefix-matched so a colocated
  `*.test.tsx` lands in the same zone as its subject.

Looser than the table, deliberately, in two places:

- **A surface may import `actions`.** The table's "may import" column omitted
  it while its "must not" column named only sibling-surface internals, and all
  seven surfaces import `actions/mutations` — 19 sites. That is the command
  layer the UI is built on. Gapping them would have produced 19 markers whose
  `closes` is "nothing", and buried the five real cross-surface breaches in
  noise. A gap that cannot name what closes it is not a gap.
- **`components/ref-autocomplete.tsx` counts as a primitive.** It sits at
  `components/` root beside `view-error-boundary.tsx`, is imported by
  `outline/{node-content,field-value}` and by a story, and had no zone
  otherwise. Its own imports (`lib` only) satisfy the primitives row, so
  admitting it costs nothing and avoids a one-file zone.

Two zones the table never had:

- **`session`** did not exist when the table was written (w5 added it). It is a
  runtime seam like `api` — `stores`, `api`, `lib` and `actions` all import it
  in production — so it takes the `lib`/`api`/`actions` row and joins that
  family as a target.
- **`shell`** is `main.tsx`, the other files directly under `src/`, and
  `components/App.tsx`. It may reach every zone below it, on the same reasoning
  as `layer:app` in `LAYER_ALLOWS`: a composition root wires the layers and is
  imported by nothing.

## Deviations from the brief

1. **The gap-node resolver is not called from `ui-boundaries`.** The brief's
   second axis was "every `GAP [[id]]` on an import line names an existing
   `#gap` node (reuse the resolver)". The resolver lives inside
   `harness/tests/gap-markers-resolve.test.ts`; importing a `*.test.ts` from
   another test file re-registers its `describe` blocks under the importer, and
   moving it to `src/` would edit a file this wave does not own. It is also
   already covered: `gap-markers-resolve` scans every `.ts`/`.tsx` in the
   workspace, these markers included, and it is green. `ui-boundaries` asserts
   the two axes that check does *not* cover — every breach carries a marker,
   and no marker sanctions an import the matrix already allows (a stale
   sanction reads as covered and is not). A second resolver here would have
   been a second mechanism for one rule.
2. **`enforcement` on the new `#rule` node is `prose`, per the brief**, with
   `gate` = `harness ui-boundaries`. Flagging the tension: after `b3086d0` the
   harness *does* check this rule, and `docs/kb/rules.md`'s own header says
   "`prose` means nothing checks it". The existing data is split on this —
   *Module boundaries* and *Isomorphism fence* say `harness`, while *Public
   surface*, *Skip pairing* and *No conflict markers* say `prose` with a
   harness gate for checks that exist. I asked the owner and had no answer
   before finishing, so I followed the brief's literal instruction ("wave c1
   derives it"). One `kb set` flips it if c1 wants `harness` sooner.
