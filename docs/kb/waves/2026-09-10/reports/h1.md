# h1-ui-test-isolation — report

Branch `kb-h1-ui-tests` from `main` @ `7ba61cd`. Harness: claude / opus.
Gate: `intent/gate.sh session claude` → 0 (`SOFT_MISSING: shellcheck
actionlint nvfetcher`).

**Result: 5/5 and 5/5.** `bun run test:ui` five times with `bun test packages`
running beside it: 117/117 files, 1054/1054 tests, five times. `bun test
packages` five times under `bun run test:ui`: 483 pass / 0 fail / 2 skip,
five times. Both gaps closed; gap 1 re-scoped, because its stated mechanism
was wrong.

---

## Root cause, in one sentence

`activateNode` arms a 250 ms wall-clock `fallBackFromMissingHost` that clears
`activeNodeId` when no text host registers for the row, and the suites that
drive the keymap or the store directly never mounted one for the row they
crossed to — so under load the timer beat the assertion.

Nothing was shared between files, and file parallelism was not the trigger.

---

## Diagnosis

### The gap's stated mechanism, and why it is not the one

The gap's `current` said: *"Vitest schedules the 105 ui files across workers
that share module state: a suite whose `void mutations.X().then(...)` chain is
still in flight when a neighbour asserts writes into that neighbour's store."*

Two independent measurements refute it.

**1. The counts.** `src/test-support/pairing-counts.sh` (committed) runs a file
set N times solo, paired, and paired with `--no-file-parallelism`:

| lane | before the fix | after |
|---|---:|---:|
| `use-node-keydown.characterization` alone | 0/10 red | 0/10 |
| `editor-behavior` alone | — | 0/10 |
| the pair, parallel | 6/10 red | 0/10 |
| the pair, `--no-file-parallelism` | 3/10 red | 0/10 |

A **sequential** pair that still reddens cannot be a file-parallelism defect.
The sequential reds were also worse in kind: 3 runs carried 4 failures across
two tests (`bare ArrowUp crosses to the previous visible row`,
`Meta+ArrowDown on a row with nothing to reveal is claimed and inert`), where
the parallel reds were all the first one.

**2. The instrumentation.** `src/test-support/isolation-probe.ts` (committed,
with `isolation.a.test.ts` / `isolation.b.test.ts`) records from inside each
file: `process.pid`, a nonce minted per **realm** (`globalThis`), a nonce
minted per **module registry**, and the identity of the `useOutlineStore`
object its registry resolved. It then asserts that no neighbour sharing its
realm shares its registry or its store, and that its own store is pristine.

```
| file | pid | realm | module | store | inherited window |
|---|---:|---|---|---|---|
| isolation.b | 12562 | twa0xi4s | pw720er5 | sj1tz13f | false |
| isolation.a | 12563 | 75u1dexi | 73flgls8 | pb8bv4tg | false |
```

That is with `--no-file-parallelism --max-workers=1`. Different pids: `vp
test` (vitest 4.1.10, `isolate: true` by default) forks a **process per
file**. Two ui test files never share a realm, let alone a module registry or
a store object. The `void mutations.X().then(…)` chain a file leaves in flight
cannot reach another file, because there is no other file in that process.

Nothing in the `test:` block needed to change, so there is no UI-run wall-time
before/after to report.

### What it actually was

`use-node-keydown.characterization.test.tsx` mounts a bare `contenteditable`
`Host` — deliberately, because `isRef` and the caret are inputs to the keymap
and driving them directly is what makes the ref-instance rows reachable. That
host is not a `NodeTextHost`, so it never calls `registerTextHost`.

`outline.store.ts` `activateNode`:

```ts
window.setTimeout(() => fallBackFromMissingHost(key), 250);
```

`fallBackFromMissingHost` sets `activeNodeId: null` unless the key is in
`mountedTextHosts`. In the app the timer never fires, because every visible
row mounts a host that registers the moment its row becomes active. In the
suite it always eventually fires; the test only passed when it read the store
within 250 ms of the activation.

The correlation is exact. Across ten paired runs, the DEV warning
`kb: active text host did not mount: tree/n.root-b` appeared in the five runs
that failed and in none of the five that passed — `warn=1 fail=1` or
`warn=0 fail=0`, every run, and `warn=0` in all ten solo runs.

`editor-behavior.test.tsx` §3.3 has the same shape from the other direction:
it calls `activateNode("n.root-b", 0)` without rendering anything at all, so
`n.root-b` has no host either. It failed once in five loaded runs with the
same `expected null to be 'n.root-b'`.

## The fix

`src/test-support/active-text-host.ts` — one helper, called from the
`beforeEach` of the suites that render one row or none:

```ts
const unmountTextHost = mountActiveTextHost();   // beforeEach
unmountTextHost();                               // afterEach
```

It follows the store's `activeInstanceKey` and registers a host for it, which
is the invariant `outline.store` is written against: *whatever row is active
has a mounted host*. It follows the store rather than React — the registry
only asks whether the key is in `mountedTextHosts`, and a subscription
registers in the same tick as the activation instead of one commit later,
which also keeps it off the suite's own root where a `root.render` would
displace it.

**Why this is the root and not a budget.** The alternative fixes all leave the
defect in place: turning file isolation on changes nothing (it is already on);
draining mutation chains in `afterEach` is about a different hazard, and the
suite already does it; widening the test's own budget past 250 ms would mean
asserting against a state the store has legitimately torn down. The suite was
modelling an outline without the one thing every outline row has.

**Assertions tightened, not loosened.** The two crossing-row tests used to
poll:

```ts
expect(await activeNodeSettlingOn("n.root-b")).toBe("n.root-b");
```

`activeNodeSettlingOn` was added by an earlier wave to outrun this timer.
Outliving a race is not winning it, so it is deleted; the tests now read the
store once, straight after the chord:

```ts
expect(useOutlineStore.getState().activeNodeId).toBe("n.root-b");
```

That is 0/10 red paired and sequential.

`ui/src/actions/mutations.ts` was **not** touched. The evidence never pointed
there: no fire-and-forget chain crosses a file, and within the file the
suite's `settle()` already awaits them.

## Calls I made

- **Re-scoped gap 1 rather than closing it as written.** Its `current`
  asserted a mechanism the measurements refute. Keeping the id and rewriting
  `expected` / `current` / `impact` / `closes` (and the node text, which also
  named the wrong mechanism) leaves the record honest instead of leaving a
  "done" gap that would teach the next reader the wrong thing.
- **Deleted `activeNodeSettlingOn` instead of leaving it.** It was a
  workaround for exactly the race the fix removes; keeping it would be a
  second mechanism for a solved problem, and it weakened the assertion.
- **One helper, not a component.** `mountActiveTextHost` follows the store
  rather than rendering a React component: a `.tsx` component in
  `test-support/` trips `react(only-export-components)` when the file also
  exports the mount function, and splitting one concept across two files to
  satisfy a fast-refresh rule is worse than not needing React at all. The
  store subscription is also strictly earlier than a commit, which is what
  the registry checks.
- **Did not add `test:ui:perf`.** The brief offered it as the fallback for
  palette-index; the ratio shape was already in place and only needed a
  better estimator, so a second lane would have been a parallel path for a
  concept that already has one.
- **Left `PASS_BUDGET` at 8.** Sizing it up would have masked the real issue
  (sample count), and sizing it down is not what the evidence supports.
- **Did not touch `mutations.ts`, any component, store, or lib source.** The
  evidence never pointed there.

## Seams I did not take

- **The 250 ms fallback is a wall-clock timer in production code.**
  `activateNode` and `unregisterTextHost` both arm
  `window.setTimeout(fallBackFromMissingHost, 250)`. It is correct behaviour
  and out of my ownership, but it is a real seam: a suite can only observe it
  by racing it, and the app cannot test the fallback itself without waiting a
  quarter second. If it ever grows a test, that test needs an injectable
  clock, not a longer budget. Not filed as a gap — it is design, not drift —
  but worth a look when `outline.store` is next opened.
- **`editor-behavior.test.tsx` installs DOM globals in `beforeAll` and never
  restores them**, unlike the five files that use `installDomGlobals`. Harmless
  today because `vp test` forks a process per file, which the probe now pins;
  it would matter the day someone sets `isolate: false` for speed. The probe
  is the thing that would catch that.
