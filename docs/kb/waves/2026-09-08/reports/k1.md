## The resolver, as implemented

`allowedRefIdsOf` (`packages/domain/model/src/field-type.ts`) answers "which
nodes may fill this ref field" from **exactly one** carrier, chosen in this
order by `declaredTargetQuery`:

1. `sys.f.targetQuery` — the general form, used verbatim.
2. `sys.f.targetTag` — union of the listed tags' instances.
3. **the field node's own children** — when it declares neither and has
   children, the children are the allowed values, in child order.
4. otherwise unrestricted (`null`).

The first present carrier is the only one consulted; a field declaring two
would answer one question twice.

Clause 3 is derived into EDN by `childrenTargetQuery(fieldId)` and run through
the same injected runner as clause 1 — no TypeScript `children` walk beside the
query path:

```
[:find ?id :where [?p :node/id "<fieldId>"] [?p :node/child ?c]
                  [?p :node/child-order ?o] [?c :node/id ?id]]
```

`:node/child` paired with `:node/child-order` is the ordered-children idiom the
query compiler already collapses into one ordered projection (`collapseChildOrder`
in `packages/domain/query/src/ir/parse.ts`), so the picker lists options in the
order the outline shows them.

Clause 2 deliberately stays a scan of the caller's node set rather than a query:
it needs no engine, which is what lets every non-query surface and every test
without an index resolve a tag constraint. That asymmetry is stated in the
function's own comment so it does not read as an oversight.

One consequence worth naming: a children-declaring field with **no runner**
resolves to the empty set, not to "unrestricted" — same as any other declared
query. `packages/app/server/tests/field-target.test.ts` pins it.

## Per retired tag: what replaced it, and the grep

`grep -rn "sys\.tag\.query|sys\.tag\.ref\b|sys\.tag\.field-type|refTag|queryTag|fieldTypeTag|PINNED_TAG_TEXT|findPinnedTagId|pinnedTagIdsOn|isQueryTagBadges|enforcement-level|check-surface" packages/ harness/`
returns only prose (comments in `ext-check/src/model.ts`, `check.test.ts`,
`kinds.test.ts`) plus `queryTaggedInstances` / `queryFieldCarriers`, which are
schema-zoom helpers whose names merely contain the substring. No reader remains.

| tag | replaced by | reader now |
|---|---|---|
| `sys.tag.field-type` | `sys.ft.*` are children of `sys.f.fieldType` | `allowedRefIdsOf` clause 3 |
| `sys.tag.query` | `sys.f.query` present | `isQueryNode` / `hasQueryDef` (`lib/query-node.ts`), and the ⌕ bullet via `BulletModeInput.fieldIds` |
| `sys.tag.ref` | `sys.f.ref.target` present | `contextualTargetOf` (`lib/contextual-ref.ts`) |
| `#pinned` (user tag) | children of the seeded `pinned` node, each a contextual reference | `lib/pinned.ts` |
| `#enforcement-level` | children of field `enforcement` | `buildCheckModel` → `fieldOptions` |
| `#check-surface` | `surface`'s `targetQuery` over those children, minus `prose` | the same query path everything else uses |

Two readers were not merely redundant but **wrong**, which is the part worth
recording:

- `query-node.ts` matched any tag whose *name* was `query`, read off
  `node.tags` — a display array that `resolveTags` deliberately strips kind refs
  from. A user tag called `query` turned its rows into live `/ws`
  subscriptions. `packages/app/ui/src/lib/query-node.test.ts` now pins the
  negative case.
- `contextual-ref.ts` required the `#ref` tag *and* the target. The tag half was
  strictly weaker (a `#ref` with no target is not a reference either) and it
  read `typeRefsOf`, so an ontology-scoped wire set that did not include the tag
  node stopped resolving references. The new test
  ("resolves with no seed nodes present at all") is that case.

## Kinds by carrier, and the bullet

`isQueryNode(node)` ⇔ `sys.f.query` is present in `props`.
`contextualTargetOf(node)` ⇔ `sys.f.ref.target` names a non-empty node id.
`resolveBulletKind` reads a new `fieldIds` input (the node's prop keys) so the
glyph reads the same carrier the predicate does — previously it matched the tag
name and could disagree with `isQueryNode`.

The palette gestures now set one prop and nothing else. Both are still
`node.update` under the hood, so undo is unchanged.

## How the query-node empty state is edited now

Unchanged, and deliberately so. *Turn into query* and `planNewQueryNode` both
write `sys.f.query = DEFAULT_QUERY_EDN`, so a fresh query node is never empty;
the EDN is edited through the per-node **debug fields** switch (⌘K → "Show debug
fields"), because `sys.f.query` is a `sys.`-prefixed prop and
`isIntrinsicSystemPropKey` hides those from ordinary field rows.

That was already true with the tag. `#query` templated `sys.f.query` and
`sys.f.query.limit`, but `resolveVisibleProps` filters templated slots through
the same `isPropHiddenByDefault`, so the template surfaced nothing the debug
switch did not. Removing the tag therefore loses no affordance, and no new
visibility rule was added — the brief's instruction, followed literally.

## Pinned

`lib/pinned.ts` is rewritten around the seeded `pinned` node's children, each an
ordinary contextual reference. Its header comment answers the old one directly:
the tag argument (costs nothing until first pin; membership through `typeRefsOf`
not badges) was true but beside the point — the tag named no concept.

What the list buys: **order is data** (a tag is a set, so the sidebar sorted by
label and "put my inbox first" was inexpressible), **one node kind reused** (a
pin *is* a contextual reference — backlinks count it, the outline renders it),
and **nothing is written to the pinned node**.

**Reorder by drag: free, and it does reach the sidebar.** The Pinned list is an
ordinary outline node, so the existing child reorder writes its child order, and
`listPinnedNodes` returns children in stored order. Nothing was built for it.

## Calls I made

- **The Pinned list is `pinned`, not `sys.pinned`** (brief §3 said `sys.pinned`).
  Every pin writes a child into that node, which is exactly what the `sys.*`
  write guard refuses; threading `force` through `node.add`/`node.remove` for
  this one caller would have been the special case Rule 1 forbids. The
  `lens.all-mentions` seed already established the precedent and states the
  reason in `SYSTEM_IDS`. Being an ordinary node is also what makes the list
  draggable in the outline, which is where its order comes from.
- **`togglePin` no longer refuses `sys.*` targets.** The guard existed because
  tagging wrote to the node's kind slot; pointing a reference at a node is not a
  write, and `sys.*` browse has always been open. Keeping the guard would have
  been a rule with no remaining reason. `pin.test.ts` asserts the new behaviour
  with that reasoning inline.
- **`ensureSystemSeed` grew a structural pass, not a one-shot migration.**
  `adoptSeedChildren` adopts seed-declared children that nothing currently
  parents — the exact mirror of the existing fill-absent props pass. Without it
  the seed would declare parentage that no existing store ever gets, i.e. a dead
  seam. Only orphans are adopted: a node the owner already filed somewhere is
  their arrangement, and a second parent is a `txIntegrityError`. This is why
  the migration script has no reparenting step for `sys.ft.*`.
- **The `surface` field keeps a `targetQuery` rather than becoming a child set.**
  Its options are a *subset* of another field's children (everything but
  `prose`), and a query says that once; a second child list would be the mirror
  Rule 1 warns about.
- **`packages/domain/model/tests/kinds.test.ts` is a new file** (the brief did
  not name one). It owns the general claim; the runtime contextual-ref test was
  narrowed to the `#ref` case so the two do not restate each other.
- Stale fixtures removed rather than rewritten: `fixtures/graph.ts` dropped its
  `sys.tag.query` node and `bullet.stories.tsx` now stubs a query node with the
  field. That moved three pinned row counts in `ds/schema-compat.test.ts`
  (`list-all` 52→51, `list-tags` 3→2, `query-node.default` 52→51) — one fewer
  node, one fewer tag, and the counts were re-pinned deliberately.
- `AGENTS.md`'s ext-check removal recipe was corrected (it named
  `check-surface` nodes that no longer exist).
- `DESIGN-UI.md`'s "(i12)" heading became "(2026-08-27)" per the brief; nothing
  linked to the old anchor (`grep -rn "contextual-references-i12"` is empty).

## The `#rule` node — no real check, and why

`01M1VVCK3CJ9PJ3PKGP6EXGYPH`, `home` = `tools/kb/DESIGN.md#kinds-roles-and-options`,
`scope` = `tools/kb`, **`enforcement` = `prose`**. No `#check` was minted.

The brief offered one: a `@kb/model` test asserting that no seeded `sys.tag.*`
templates zero fields *and* is referenced by no `targetTag`. That conjunction is
too weak to stand as this rule's enforcement — it would have caught neither of
the tags this wave actually retired. `sys.tag.field-type` templated zero fields
but *was* a `targetTag` referent, so it passes; `sys.tag.ref` and
`sys.tag.query` each templated a real field, so they pass too. A check that
would not have failed on the very drift the rule exists to prevent is not
enforcement.

What *is* mechanically decidable is one of the rule's three clauses — an option
set is expressed by parenting, so no supertag exists whose only job is to be a
`targetTag` referent. That is pinned by the new
`packages/domain/model/tests/kinds.test.ts`, which asserts every seeded supertag
templates at least one field and no `targetTag` points at one that does not.
That test *would* have failed on `sys.tag.field-type`.

It is left as an ordinary regression test and **not** minted as a `#check`,
because `enforcement` is one value for the whole rule and the other two clauses
are the strip test — a reviewer judgement, not something a harness can decide.
Claiming `harness` for a rule whose load-bearing half nothing checks is exactly
the aspirational enforcement the rules index forbids. The `gate` field records
what would close it.
